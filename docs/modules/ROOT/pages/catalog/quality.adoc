= 데이터 품질
:toc: macro
:toclevels: 2

데이터가 믿을 만한지 확인하려면 두 가지가 필요합니다. 하나는 실제 값이 어떻게 분포하는지 들여다보는 일이고,
다른 하나는 그 분포가 기준을 지키는지 따져 보는 일입니다. 데이터 품질 기능은 컬럼 통계를 수집하는 *프로파일링* 과,
규칙으로 데이터를 평가하는 *정밀 진단* 을 데이터셋 상세의 *품질* 탭 한 화면에서 제공합니다.

프로파일과 정밀 진단은 모두 *품질 워커* 가 원본 전체 데이터로 합니다. 카탈로그에 Trino 가 연결된 데이터셋은 Trino 로 집계하고,
연결이 없으면 원본 DB(PostgreSQL · MySQL · MariaDB · Oracle · SQL Server)를 직접 읽습니다. 정해진 주기로 진단하려면
<<help-quality-jobs,품질 진단 작업>> 에 데이터셋을 대상으로 등록합니다.

.프로파일·정밀 진단과 알림
image::diagrams/catalog-quality-01.png[프로파일·정밀 진단과 알림,role="diagram"]

image::catalog-quality/dashboard.png[품질 탭 — 점수 영역 · 결과 표 · 규칙 목록, 900]

이 문서는 처음 사용하는 분을 기준으로 화면 순서대로 설명합니다.
**고급 사용자** 상자는 몰라도 사용에 지장이 없는 심화 내용이니 처음에는 건너뛰어도 됩니다.

== 시작하기 전에

=== 이런 일을 할 수 있습니다

* **프로파일** — 품질 워커가 Trino 또는 원본 DB 로 컬럼별 NULL 비율 · 고유 비율 · 값 범위를 수집합니다.
* **규칙 만들기** — NULL 없음 · 고유값 · 값 범위 · 행 수 · 최신성 같은 품질 규칙을 직접 만들거나 추천받습니다.
* **진단과 점수** — 규칙을 진단해 품질 점수와 데이터셋 품질 상태(GOOD · WARN · BAD)를 얻습니다.
* **주기 진단** — 관리 › 데이터 품질의 품질 진단 작업으로 매시간 · 매일 · 매주 · 매월 자동으로 진단합니다.
* **원천 문제 추적** — 리니지상 원천 데이터셋의 품질 문제를 경고로 봅니다.

=== 먼저 알아 둘 용어

[cols="1,4",options="header"]
|===
| 용어 | 뜻

| 프로파일
| 원본에서 수집한 컬럼 통계의 *스냅숏* 입니다. 원본이 바뀌면 다시 수집해야 합니다.
| 품질 규칙
| 데이터가 지켜야 할 기준입니다(22종). 심각도는 *치명* · *경고* · *정보* 중 하나입니다.
| 품질 지표
| 미리 정해 두고 여러 컬럼에 할당하는 품질 기준입니다(예: *여부 Y/N*, *날짜 YYYYMMDD*). 지표를 컬럼에 할당하면 그 컬럼에 규칙이 생기고,
지표의 기준을 바꾸면 할당된 모든 컬럼의 규칙이 함께 바뀝니다.
| 진단 기준
| 지표와 규칙을 공공데이터 관리지침의 품질진단 기준 이름(날짜 · 여부 · 금액 · 필수값 …)으로 묶은 것입니다(예전 화면 이름 "분류"). 품질 진단 작업과 리포트가 이 이름으로 고르고 집계합니다.
| 정밀 진단
| 품질 워커가 원본 전체 데이터로 규칙을 판정하는 실행입니다. Trino 경로와 원천 직접 경로가 있습니다.
| 품질 워커
| 진단 · 프로파일 쿼리를 내는 별도 프로그램입니다. 카탈로그의 대기열에서 실행을 가져가 처리합니다.
| 미평가
| 아직 판정 결과가 없어 점수 계산에서 빠진 규칙입니다.
|===

=== 메뉴 위치

*데이터 카탈로그 → 데이터셋* 에서 데이터셋을 열고 *품질* 탭을 누릅니다. 데이터셋 상세 화면 전체는
xref:catalog/datasets.adoc[데이터셋] 에서 설명합니다.

=== 누가 무엇을 할 수 있나요

탭을 보는 것(품질 점수 · 점수 추세 · 진단 결과 · 규칙 목록 · 프로파일 표 · 진단 상태)은 로그인한 사용자 누구나 할 수 있습니다.

진단을 돌리거나 규칙 · 프로파일을 바꾸는 버튼은 *데이터셋의 소유자(등록한 사람) 또는 관리자* 만 씁니다. 소유자가 아니면
*정밀 진단* 버튼은 누를 수 없게 흐리게 보이고(마우스를 올리면 이유가 나옵니다), 나머지 버튼은 나타나지 않습니다.
소유자 또는 관리자라도 아래 기능 권한이 있어야 합니다.

[cols="1,3"]
|===
| 작업 | 필요한 기능 권한

| *프로파일 실행* · *프로파일 갱신* · *정밀 진단*
| *품질 진단 실행* (`quality.run`)
| *규칙 추가* · *규칙 추천*, 규칙 편집 · 삭제
| *품질 규칙 관리* (`quality.rules-manage`)
| 품질 진단 작업에 주기 정하기
| *진단 주기 설정* (`quality.schedule`) — <<help-quality-jobs,품질 진단 작업>> 참고
| 원천 데이터 시간대 설정
| 관리자만
|===

데이터 품질 메뉴의 *품질 지표* 탭에서 지표를 컬럼에 할당 · 해제하는 것도 그 컬럼의 데이터셋마다 소유자 또는 관리자여야 합니다.

세 기능 권한은 *기본 허용형* 입니다. xref:ops/permissions.adoc[권한 관리] 의 *기능 권한* 표에서 아무 역할도
제한하지 않으면 로그인 사용자 모두 쓸 수 있고, 특정 역할의 체크를 해제하면 그 역할 사용자에게는 해당 버튼이
보이지 않습니다.

image::catalog-quality/feature-permissions.png[권한 관리 — 데이터셋 그룹의 품질 규칙 관리 · 품질 진단 실행 · 진단 주기 설정, 900]

소유자가 아니거나 권한이 없는 사용자에게는 *프로파일 실행(갱신)* · *지표 할당* · *규칙 추가* · *규칙 추천* 버튼과 규칙의 편집 · 삭제 아이콘이 보이지 않습니다.
점수 · 결과 · 규칙 · 프로파일과 규칙의 *진단 쿼리 보기*(`</>`)는 그대로 볼 수 있습니다.

image::catalog-quality/read-only.png[소유자가 아닌 사용자의 품질 탭 — 정밀 진단은 흐리게 · 규칙에는 진단 쿼리 보기만 남음, 900]

== 품질 탭 화면 구성 [[help-dataset-quality]]

품질 탭은 *품질 진단* 과 *데이터 프로파일* 두 구역으로 나뉩니다. 품질 진단은 규칙으로 데이터가 기준을 지키는지 판정하는 곳이고
(결과가 품질 점수가 됩니다), 데이터 프로파일은 컬럼별 통계로 분포를 보는 곳입니다(판정이 아니며 점수를 바꾸지 않습니다).
위에서부터 다음 순서로 구성됩니다. 해당 내용이 없으면 그 영역은 나타나지 않습니다.

[cols="1,3"]
|===
| 영역 | 내용

| 업스트림 품질 경고
| 리니지상 원천 데이터셋 중 품질 상태가 나쁜 것이 있을 때만 보입니다. <<_업스트림_품질_경고,업스트림 품질 경고>> 참고.
| 품질 진단 — 품질 점수 영역
| 점수와 막대, 통과 · 실패 · 전체 개수, 점수 추세, 마지막 진단 시각, *주기 진단 설정* 바로가기, 실행 버튼이 모여 있는 품질 대시보드입니다.
| 품질 진단 — 결과 표
| 규칙별 최신 판정입니다. 상태 · 규칙 · 기준 방식 · 컬럼 · 실제 값 · 상세 · 심각도를 보여 줍니다.
| 품질 진단 — 규칙 (N)
| 등록된 규칙 목록입니다. 품질 지표를 할당해 생긴 규칙에는 지표 이름이, 이 데이터셋에서 직접 만든 규칙에는 *직접 정의* 가
붙습니다. 직접 정의한 규칙의 기준은 그 규칙에서, 지표를 할당한 규칙의 기준은 지표에서 바꿉니다. 편집 · 삭제 아이콘이 있습니다.
| 데이터 프로파일
| 구역 머리에 행 수 · 프로파일한 시각과 *프로파일 실행*(이미 있으면 *프로파일 갱신*) 버튼이 있고, 그 아래 최신 프로파일의 컬럼별 통계 표가 있습니다.
프로파일이 아직 없으면 *아직 프로파일이 없습니다.* 가 보입니다.
| 도움말
| *도움말 — 품질 진단과 데이터 프로파일은 어떻게 동작하나요?* 를 누르면 권장 순서, 규칙 유형, 커스텀 Python 작성법이 펼쳐집니다.
|===

=== 품질 점수 영역 (품질 대시보드)

image::catalog-quality/batch-result.png[품질 점수 영역 — 점수와 막대 · 통과 / 실패 / 전체 개수 · 점수 추세 · 실행 버튼, 900]

* *품질 점수* — 아직 진단한 적이 없거나 평가된 규칙이 없으면 `—` 로 표시됩니다. 막대는 80% 이상이면 초록, 50% 이상이면 주황, 그 아래는 빨강입니다.
* *통과 · 실패 · 전체 N개* — 체크 아이콘이 통과, X 아이콘이 실패 규칙 수입니다. *전체* 는 점수 계산에 들어간 규칙 수로,
  미평가 규칙은 빠집니다.
* *점수 추세* — 진단이 2회 이상 쌓이면 최근 20회까지의 점수를 선으로 보여 주고 옆에 *최근 N회* 를 표시합니다.
  직전 진단보다 점수가 바뀌면 `▲ 10.0%p`(초록) 또는 `▼ 26.7%p`(빨강)처럼 변화폭이 함께 나옵니다.
* *마지막 진단* — `방금 전`, `10분 전`, `23시간 전` 처럼 마지막 점수 산출 시각입니다.
* *주기 진단 설정 →* — 관리 › 데이터 품질의 품질 진단 작업 탭으로 갑니다(그 메뉴를 열 수 있는 사람에게만 보임). <<_진단_주기,진단 주기>> 참고.
* *정밀 진단* · *지표 할당* · *규칙 추가* · *규칙 추천* — 각 기능은 아래 절에서 설명합니다. 정밀 진단 버튼에 마우스를 올리면
  무엇을 하는지(무엇으로 평가하는지 · 평가하지 못하는 규칙 · 걸리는 시간)가 나옵니다. 실행 중에는 버튼이
  *진단 중…* 으로 바뀌고 다시 누를 수 없습니다. 프로파일 버튼은 여기가 아니라 아래 *데이터 프로파일* 구역에 있습니다.

== 프로파일링

프로파일은 테이블 전체에 통계 SQL 을 실행해 컬럼별 분포를 수집한 *스냅숏* 입니다. 규칙 판정이 아니라
통계이므로 품질 점수를 바꾸지 않습니다. 품질 탭 아래쪽 *데이터 프로파일* 구역의 *프로파일 실행* 버튼으로 수집하고,
이미 프로파일이 있으면 버튼이 *프로파일 갱신* 으로 바뀝니다.

프로파일은 *정밀 진단* 과 같은 대기열에 들어가 *품질 워커* 가 실행합니다. 경로도 정밀 진단과 같습니다 — 카탈로그에 Trino 가
연결돼 있으면 Trino 로, 없으면(PostgreSQL · MySQL · MariaDB · Oracle · SQL Server) 품질 워커가 원본 DB 에 직접 집계 쿼리를 냅니다
(xref:#help-quality-trino[정밀 진단]). 모든 컬럼의 통계를 쿼리 하나로 세고, 고유값이 20개 이하인 컬럼만 최빈값 쿼리를 하나씩 더 냅니다.
진행 상태는 데이터 프로파일 구역의 상태 카드(진행 막대 · 경과 시간 · *프로파일 중지*)에 나오고, 실행 중에는 버튼이 *프로파일링…* 으로 바뀌며 정밀 진단과 프로파일 모두
다시 누를 수 없습니다. 관리 > 데이터 품질 > 실행 현황에도 *프로파일* 표시와 함께 나옵니다.

image::catalog-quality/empty-state.png[규칙이 없는 데이터셋의 품질 탭 — 데이터 프로파일 · 규칙 추가, 900]

끝나면 구역 머리에 행 수 · 프로파일한 시각이 보이고 그 아래 통계 표가 나타납니다. 데이터셋의 *행 수* 도 이 값으로 갱신됩니다
(정밀 진단도 끝날 때 전체 행 수로 갱신합니다 — 원천 직접 경로가 행 수 상한에 걸린 실행은 제외).

image::catalog-quality/profile.png[데이터 프로파일 표 — NULL 이 있는 컬럼의 비율을 빨간색으로 강조, 900]

[cols="1,3"]
|===
| 열 | 내용

| 컬럼 · 타입
| 컬럼 이름과 카탈로그에 등록된 타입입니다.
| NULL
| NULL 비율입니다. 0% 보다 크면 빨간색으로 강조됩니다.
| 고유
| 고유 값 비율입니다.
| 최소 · 최대
| 최솟값 · 최댓값입니다. 긴 문자열은 말줄임으로 표시되고, 마우스를 올리면 전체 값이 보입니다.
| 평균
| 숫자형 컬럼만 계산합니다.
| 최빈값
| 고유 값이 20개 이하인 코드성 컬럼의 상위 5개 값과 건수(예: `BRONZE ×2`)입니다.
|===

바이너리 컬럼은 *바이너리 — 통계 생략* 으로 표시됩니다.

[NOTE]
====
* 프로파일할 수 있는 데이터셋은 정밀 진단과 같습니다 — Trino 가 연결돼 있거나, 원본이 PostgreSQL · MySQL · MariaDB · Oracle · SQL Server 여야 합니다.
  스키마(컬럼) 정보가 없으면 요청할 수 없습니다(먼저 메타데이터 동기화). 그 밖의 원본은 Trino 에 카탈로그로 등록하고 *카탈로그 연결* 로 이어야 합니다.
* 통계를 낼 수 없는 컬럼(Trino 에서 비교할 수 없는 타입 등)이 있으면 그 컬럼만 이름 · 타입으로 남기고 실행 상태가 *일부 실패* 가 됩니다.
  쿼리가 모두 실패하면(접속 · 권한 · 테이블 이름 문제) 프로파일을 남기지 않고 *실패* 로 끝납니다 — 예전처럼 통계 없는 프로파일로 대체하지 않습니다.
* 두 경로의 건수(행 수 · NULL · 고유값 · 평균)는 같습니다. 값의 표기는 Trino 의 타입에 따라 조금 다를 수 있습니다 — 예: MySQL
  `TIMESTAMP` 는 Trino 경로에서 `2006-02-15 05:03:42+00:00`(UTC), 원천 직접 경로에서 `2006-02-15 05:03:42`, MySQL `YEAR` 는 Trino 경로에서
  날짜(`2006-01-01`)로 보이고 평균은 계산하지 않습니다. 문자열의 고유값 수 · 최소 · 최대 · 최빈값은 두 경로 모두 대소문자 · 끝 공백을
  구분하고 문자 코드 순서로 셉니다 — 원천 직접 경로도 MySQL · MariaDB 의 기본 정렬 규칙(대소문자 무시)을 따르지 않습니다.
* 프로파일은 실행 시점의 스냅숏입니다. 규칙 판정에는 쓰지 않으므로(정밀 진단은 원본 전체를 다시 읽습니다) 분포를 보거나
  *규칙 추천* 을 받을 때 갱신하면 됩니다.
* 최소 · 최대 · 최빈값은 실제 데이터 값이라 *샘플 데이터 조회* (`datasets.sample-view`) 권한이 있어야 보입니다. 권한이 없으면 그 칸이
  `—` 로 비고 머리에 *최소 · 최대 · 최빈값은 샘플 보기 권한이 있어야 보입니다* 가 나옵니다. 행 수 · NULL · 고유 · 평균은 그대로 보입니다.

== 품질 규칙

=== 규칙 유형

규칙 유형은 모두 22종입니다 — 아래 기본 유형과 관리지침 진단 기준 · AI-Ready 를 위한 유형(날짜 형식 · 컬럼 간 비교 · 참조관계 · 글자 깨짐 · 공백 · 논리관계 ·
계산식 · 더미 값 · 연속성 · 값 분포 다양성 · 여러 컬럼 키 · Trino 함수 — <<help-quality-trino,정밀 진단>> 참고)입니다. 모두 정밀 진단이 평가합니다. *규칙 추가* 대화상자는 데이터 품질 메뉴의 품질 지표와 같이 *진단 기준*(무엇을 보는가 — 공공데이터 관리지침의 진단 기준)을 먼저 고르고, 그 진단 기준 안에서
*기준 방식*(어떻게 보는가 — 아래 화면 이름)을 고릅니다. 고르면 바로 아래에 진단 기준과 기준 방식의 설명이 나옵니다. 최신성 · 커스텀 SQL ·
커스텀 Python 은 관리지침 진단 기준 밖이라 *진단 기준 없음* 에 있습니다. 화면에는 유형 코드 대신 화면 이름이 보이고, 마우스를 올리면 코드가 나옵니다.

[cols="2,4,1,1",options="header"]
|===
| 유형 (화면 이름) | 통과 조건 | Trino 경로 | 원천 직접

| `NOT_NULL` (NULL 없음) | 비-NULL 비율 ≥ 임계값(%) | ✓ | ✓
| `UNIQUE` (고유값) | 고유 값 비율 ≥ 임계값(%) | ✓ | ✓
| `MIN_VALUE` (하한 (이상)) | 최솟값 ≥ 기대값 (예: 금액 ≥ 0) | ✓ | ✓
| `MAX_VALUE` (상한 (이하)) | 최댓값 ≤ 기대값 | ✓ | ✓
| `ROW_COUNT` (행 수 하한) | 전체 행 수 ≥ 기대값. 테이블 수준이라 컬럼을 지정하지 않습니다. | ✓ | ✓
| `FRESHNESS` (최신성) | 시각 컬럼의 최댓값 이후 경과 시간 ≤ 기대값(시간, 기본 24) — 아래 설명 참고 | ✓ | ✓
| `ACCEPTED_VALUES` (허용 값 목록) | 값이 허용 값 목록 안에만 있음 (예: `G` · `PG` · `PG-13` — 값을 하나씩 적고 Enter 로 배지를 만들며, 값 안의 쉼표도 그대로 씁니다. 예: `1,000`). 값 대신 데이터 표준의 *코드 그룹* 을 고를 수 있습니다(<<_표준_코드_그룹을_허용_값으로,아래>>) | ✓ | ✓
| `REGEX` (정규식 패턴) | 값이 정규식과 일치 (예: `^[^@]+@[^@]+$`) | ✓ | ✓
| `CUSTOM_SQL` (커스텀 SQL) | 직접 작성한 SELECT 쿼리의 첫 행 첫 컬럼(위반 건수)이 0 | ✓ | —
| `CUSTOM_PYTHON` (커스텀 Python) | 플러그인 함수가 통과를 반환 — 플러그인은 품질 워커의 `custom_checks/` | — | ✓
|===

경로에서 빠지는 유형(`—`)은 그 데이터셋의 정밀 진단에서 건너뛰고 직전 결과를 이어받습니다. 규칙 목록에 *정밀 진단 제외* 가 붙습니다
(<<_미평가와_이어받기,미평가와 이어받기>> 참고).

*임계값(%)* 은 `NOT_NULL` · `UNIQUE` 에서만 씁니다.::
* 0 ~ 100 사이 값이며 기본은 100(NULL · 중복을 1건도 허용하지 않음)입니다. 다른 유형에서는 입력란이 비활성이고
  규칙 목록에도 임계값이 표시되지 않습니다.
* `0` 도 그대로 적용됩니다. 임계값 0 인 규칙은 비율과 관계없이 통과하므로 추이만 보고 싶은 컬럼에 쓸 수 있습니다.
* 판정은 반올림한 비율이 아니라 *정확한 건수* 로 합니다. 예를 들어 16,044행 중 NULL 이 183건이면 비율은 98.9% 로 보이지만
  임계값 98.86 에서는 실패, 98.85 에서는 통과입니다. 결과 상세에 `NULL 183건 / 16,044행` 처럼 건수가 함께 표시되니 이것으로 구분하세요.

image::catalog-quality/threshold-results.png[임계값에 따른 판정 — NULL 이 103건 있는 phone_no 는 비-NULL 96.6% 가 임계값 95% 이상이라 통과, 임계값 100% 인 규칙은 1건도 허용하지 않음, 900]

*FRESHNESS* 는 적재 · 수정 시각 컬럼(예: `updated_at`, `last_update`)을 꼭 지정합니다.::
* 정밀 진단이 그 컬럼의 *최댓값(가장 최근 데이터 시각)* 을 전체 데이터에서 구하고, 결과를 받은 시각까지 지난 시간으로 판정합니다.
  적재가 멈추면 시간이 지날수록 실패로 바뀝니다. 상세에 `최신 데이터(last_update 최댓값 2006-02-15 05:03:42) 이후 …시간 (허용 24시간, …)` 처럼 나옵니다.
* 시간대 정보가 없는 값(MySQL `DATETIME` 등)은 <<_원천_데이터_시간대,원천 데이터 시간대>>(기본 Asia/Seoul)의 시각으로 해석합니다.
  미래 시각(시간대 차이 등)은 0시간으로 봅니다.
* 예전에 컬럼 없이 만든 최신성 규칙은 정밀 진단에서 *최신성 검사는 적재 · 수정 시각 컬럼을 지정해야 합니다* 로 실패합니다. 규칙을 열어 컬럼을 고르세요.

*심각도* 는 규칙을 만들 때 고르며, 목록과 결과 표에는 한글 배지로 표시됩니다.::
* `BREAKING` → *치명* — 데이터 사용 불가 수준입니다(예: PK NULL, 행 수 0). 치명 실패가 하나라도 있으면 데이터셋 상태가 *BAD* 가 됩니다.
* `WARNING` → *경고* — 주의가 필요합니다(예: NULL 비율 증가, 범위 초과). 기본값입니다.
* `INFO` → *정보* — 참고용입니다.

=== 품질 지표 할당

미리 정해 둔 품질 지표(xref:#help-quality-definitions[관리 → 데이터 품질 → 품질 지표])를 이 데이터셋의 컬럼에 할당하면 규칙을 하나씩
만들지 않아도 됩니다.

. *지표 할당* 을 누르고 지표를 고릅니다. 지표의 기준이 아래에 나옵니다.
. 할당할 컬럼을 고릅니다(여러 개). 이미 그 지표가 할당된 컬럼은 *할당됨* 으로 표시됩니다.
. 컬럼을 고르면 그 컬럼으로 실행할 *진단 쿼리* 가 나옵니다. 쿼리는 컬럼마다 컬럼 이름만 다르므로 한 번에 하나만 보입니다 —
  컬럼을 둘 이상 고르면 쿼리 위에 고른 컬럼이 단추로 나오고, 누르면 그 컬럼의 쿼리로 바뀝니다(마지막에 고른 컬럼이 먼저 보입니다).
  실제 정밀 진단은 같은 테이블의 규칙들을 쿼리 하나로 묶어 실행합니다.
. *할당* 을 누르면 컬럼마다 규칙이 생깁니다.

지표를 할당한 규칙은 목록에서 이름 옆에 지표 이름(연결 표시)이, 직접 만든 규칙은 *직접 정의* 가 붙습니다. 기준은 지표에서 바꿉니다.

=== 진단 쿼리 보기

규칙 목록에서 규칙마다 있는 *진단 쿼리 보기*(`</>`) 를 누르면 그 규칙을 진단할 때 실행하는 쿼리와 통과 판정 방법이 나옵니다.
이 데이터셋의 Trino 테이블 이름과 컬럼 타입으로 만든 것이며, 쿼리의 줄마다 무엇을 세는지(전체 행 수 · 진단 건수 · 오류 건수)가 적혀 있습니다.
카탈로그에 Trino 연결이 없어 원천을 직접 읽는 데이터셋은 제목이 *진단 쿼리 (원천 직접 · PostgreSQL)* 처럼 바뀌고, 원천 DB 방언의
쿼리가 나옵니다 — 원천이 집계로 세는 규칙은 집계 쿼리, 행을 읽어 품질 워커가 판정하는 규칙(정규식 · 문자열 날짜 형식 등)은 읽기 쿼리입니다.
이 경로가 평가하지 않는 유형(Trino 함수)은 쿼리 대신 건너뛴다는 안내가 나옵니다.
Trino 로 진단하지 않는 유형(커스텀 Python)과 미리 보기를 만들지 않는 최신성, 컬럼이 스키마에 없는 규칙은 쿼리 대신 사유가 나옵니다. 커스텀 SQL 은 적은 쿼리가
그대로 실행됩니다.
실제 진단은 같은 테이블의 규칙들을 쿼리 하나로 묶어 실행하므로 테이블을 규칙 수만큼 읽지 않습니다.

=== 규칙 추가

*규칙 추가* 를 누르면 *규칙 추가* 대화상자가 열립니다.

image::catalog-quality/rule-add.png[규칙 추가 — 허용 값 목록 입력, 900]

[cols="1,3"]
|===
| 항목 | 설명

| 규칙 이름
| 필수입니다(최대 255자). 비어 있으면 *규칙 추가* 버튼이 비활성입니다.
| 진단 기준
| 무엇을 보는 규칙인지 고릅니다(완결성 · 유효성 · 정합성 · 기타, 진단 기준 없음). 항목에 마우스를 올리면 설명이 나옵니다.
| 기준 방식
| 진단 기준 안의 규칙 유형입니다. 방식이 하나뿐인 진단 기준(필수값 → NULL 없음 등)은 고를 것이 없어 흐리게 보입니다.
  방식을 바꾸면 앞 방식의 기대값은 비워집니다.
| 컬럼 (선택)
| 데이터셋 스키마의 컬럼 목록에서 고릅니다. `ROW_COUNT` · `LOGICAL` 처럼 테이블 수준 규칙은
  *선택 안 함 (테이블 수준 — ROW_COUNT/LOGICAL/여러 컬럼 키)* 을 고릅니다. `FRESHNESS` 는 컬럼을 골라야 저장됩니다.
  `COMPOSITE_UNIQUE`(여러 컬럼 키 고유값)는 이 칸이 비활성이고, 키 컬럼을 기대값 칸에서 고릅니다.
| 기대값
| 유형에 맞는 값을 적습니다(예시가 입력란에 표시됩니다). `NOT_NULL` · `UNIQUE` 처럼 기대값을 쓰지 않는 유형은
  *이 유형은 기대값을 사용하지 않습니다* 로 비활성입니다.
| 임계값 (%)
| `NOT_NULL` · `UNIQUE` 와 더미 값 · 데이터 연속성 · 여러 컬럼 키 고유값에서만 입력합니다(기본 100).
| 심각도
| `BREAKING` · `WARNING` · `INFO` 중 하나입니다(기본 `WARNING`).
|===

*커스텀 SQL* 을 고르면 기대값 칸이 *진단 SQL* 편집기로, *커스텀 Python* 을 고르면 *플러그인 설정 (JSON)* 편집기로 바뀝니다.

image::catalog-quality/rule-custom-sql.png[커스텀 SQL — 진단 SQL 편집기, 900]

image::catalog-quality/rule-custom-python.png[커스텀 Python — 플러그인 설정 (JSON) 편집기, 900]

저장하면 대화상자가 닫히고 *규칙 '<이름>' 을(를) 추가했습니다.* 알림이 뜨며 규칙 목록에 추가됩니다.
저장에 실패하면 *규칙을 저장하지 못했습니다.* 와 서버가 알려 준 사유가 표시되고, 대화상자는 입력한 값 그대로 열려 있습니다.

image::catalog-quality/rule-add-toast.png[규칙 추가 성공 알림, 900]

TIP: 새 규칙은 다음 *정밀 진단* 부터 판정됩니다. 진단하기 전에는 결과 표에 나오지 않습니다.

=== 규칙 추천

*규칙 추천* 은 최신 프로파일 통계를 근거로 규칙 후보를 만들어 줍니다. 프로파일이 없거나 후보가 없으면
*추천할 규칙이 없습니다 — 프로파일을 먼저 수집했는지, 이미 같은 규칙이 등록돼 있지 않은지 확인하세요.* 가 표시됩니다.
샘플 데이터 조회 권한이 없으면 실제 값이 들어가는 후보(허용 값 목록)는 나오지 않고, 음수 금지 근거에도 현재 최소값을 적지 않습니다.

image::catalog-quality/recommend.png[규칙 추천 (프로파일 기반) — 후보가 모두 선택된 상태, 900]

[cols="1,3"]
|===
| 프로파일 통계 | 추천 규칙

| NULL 0% | `NOT_NULL` — 지금 깨끗한 컬럼을 계속 깨끗하게 유지
| 고유 100% (10행 이상) | `UNIQUE` — 키 후보
| 최빈값이 수집된 코드성 컬럼 | `ACCEPTED_VALUES` — 현재 값 목록을 허용 목록으로
| 숫자형 최솟값 ≥ 0 | `MIN_VALUE 0` — 음수 유입 감지
| 행 수 > 0 | `ROW_COUNT` — 현재 행 수의 90% 를 하한으로(급감 감지)
|===

후보는 기본으로 모두 선택돼 있고, 아래에 *N / N 선택* 이 표시됩니다. 추천은 *현재 데이터가 깨끗하다* 는 가정에서 나오므로,
의도된 예외가 있는 컬럼(예: 이미 잘못된 값이 섞인 코드 컬럼)은 체크를 해제하세요. *선택한 규칙 N개 추가* 를 누르면
*추천 규칙 N건을 추가했습니다.* 알림과 함께 대화상자가 닫힙니다. 일부만 만들어졌다면 만들어진 건수와 실패 사유를 알려 줍니다.

image::catalog-quality/recommend-toast.png[추천 규칙 생성 성공 알림, 900]

이미 같은 유형 · 같은 컬럼의 규칙(비활성 포함)이 있으면 그 후보는 추천에서 빠지므로, 다시 열어도 중복 후보가 나오지 않습니다.

=== 규칙 수정 · 삭제

규칙 목록 오른쪽의 연필 아이콘(*규칙 편집*)을 누르면 *규칙 수정* 대화상자가 열립니다. 항목은 추가와 같고,
*저장* 하면 *규칙 '<이름>' 을(를) 수정했습니다.* 알림이 뜹니다. 바뀐 기준은 다음 *정밀 진단* 부터 반영됩니다.

image::catalog-quality/rule-edit.png[규칙 수정 — ROW_COUNT 기대값 변경, 900]

휴지통 아이콘(*규칙 삭제*)을 누르면 확인 창이 먼저 뜹니다. *삭제* 를 눌러야 지워지며, *규칙 '<이름>' 을(를) 삭제했습니다.* 알림이 뜹니다.
삭제하면 남은 규칙의 최근 결과로 품질 점수와 데이터셋 품질 상태(GOOD · WARN · BAD)를 바로 다시 계산합니다.
새로 진단한 것이 아니므로 *마지막 진단* 시각과 점수 이력 개수는 그대로이고, 알림도 다시 나지 않습니다.
규칙을 모두 지워 평가된 규칙이 남지 않으면 품질 점수 · 품질 상태와 점수 이력이 지워져 진단 전 상태로 돌아갑니다. 진단 실행 기록은 남습니다.

image::catalog-quality/rule-delete.png[규칙 삭제 확인 — 진단 결과 이력도 함께 삭제, 900]

WARNING: 규칙을 지우면 그 규칙의 진단 결과 이력도 함께 지워집니다. 잠시 빼 두려는 것이라면 아래의 비활성화를 쓰세요.

== 진단 결과

*정밀 진단* 을 누르는 방법과 진행 상태는 <<help-quality-trino,정밀 진단>> 에서 설명합니다. 끝나면 결과를 저장하고 점수와 데이터셋 품질 상태를
갱신하며, 실패가 있으면 알림 규칙을 평가합니다.

image::catalog-quality/check-result.png[진단 결과 — 점수 영역 · 최근 실행 상태 카드 · 규칙별 결과 표 (sakila.staff), 900]

=== 결과 표 읽기

[cols="1,3",options="header"]
|===
| 상태 아이콘 | 의미

| 초록 체크 | 통과
| 빨간 X | 실패 — *실제 값* 과 *상세* 칸에 판정 근거가 표시됩니다(예: `비-NULL 80.0%, NULL 1건 / 5행 (임계값 100.0%)`).
| 회색 물음표 | *미평가 — 점수에서 제외*. 마우스를 올리면 같은 문구가 보입니다.
|===

정밀 진단이 남긴 실패에는 위반 행 샘플(최대 5행)이 함께 실립니다. *상세* 칸의 *위반 샘플 N행* 을 누르면 행이 펼쳐지고,
위반한 컬럼 값이 빨간색으로 강조됩니다. 샘플은 위반 행을 특정할 수 있는 유형에만 붙습니다 — 행 수 · 커스텀 SQL · 커스텀 Python 과
최신성, 날짜 · 시각 타입 컬럼의 날짜 형식(위반이 생길 수 없음)에는 없습니다.

* *정밀 진단 — Trino 경로*: 판정이 끝난 뒤 품질 워커가 실패한 규칙마다(한 실행에 20개까지) 위반 조건으로 행 전체를 5행까지 읽습니다.
  실행이 *완료* 로 바뀐 뒤 잠시 뒤에 샘플이 붙고, 샘플 쿼리가 실패해도 진단 결과는 그대로입니다. 고유값 규칙은 중복된 값을 가진 행을
  같은 값끼리 모아 보여 줍니다.
* *정밀 진단 — 원천 직접 경로*: 원본이 집계로 센 규칙(NULL 없음 · 고유값 · 하한 · 상한 · 허용 값 · 컬럼 간 비교)과 참조관계는 Trino 경로처럼
  판정 뒤에 원본에서 위반 행 전체를 읽습니다. 행을 읽어 판정하는 규칙(정규식 · 날짜 형식 · 글자 깨짐 · 공백 · 논리관계 · 계산식)은 읽는 동안
  위반 행을 바로 모으며, 행에는 그 실행이 읽은 컬럼(규칙이 쓰는 컬럼)만 있습니다. 이때 고유값 규칙은 앞에 나온 값과 같은 값을 가진 두 번째 행부터 모읍니다.
* 한 행에는 컬럼 30개, 값은 200자까지 남깁니다.
* 위반 샘플은 실제 데이터라 샘플 탭과 같은 *샘플 데이터 조회* (`datasets.sample-view`) 권한이 있어야 보입니다. 권한이 없으면
  건수와 상세는 그대로 나오고 샘플 자리에 *위반 샘플은 샘플 보기 권한이 있어야 보입니다* 가 나옵니다.

image::catalog-quality/failed-samples.png[위반 샘플 1행 펼침 — 위반 컬럼 password 를 빨간색으로 강조, 900]

[[_미평가와_이어받기]]
=== 미평가와 이어받기

정밀 진단이 이번에 평가하지 않은 규칙 — 그 데이터셋의 경로에서 빠지는 유형(원천 직접 경로의 커스텀 SQL · Trino 함수,
원본을 직접 읽을 수 없는 Trino 경로의 커스텀 Python)과 진단 기준(지표)을 골라 돌린 실행에서 고르지 않은 규칙 — 은 새 결과를 남기지 않습니다.

* 그 규칙의 직전 결과가 있으면 *이어받아* 점수에 반영합니다. 결과 표에서 그 규칙 이름 옆에 *이전 결과 · N일 전* 이 붙습니다.
* 직전 결과도 없으면 *미평가* 로 점수 계산에서 뺍니다. 아직 한 번도 진단하지 않은 규칙은 결과 표에 나오지 않습니다.

업그레이드 전 *간이 진단* · *품질 배치* 가 남긴 결과도 같은 방식으로, 다음 정밀 진단이 그 규칙을 평가하기 전까지 이어받습니다(두 기능은 없앴습니다).

== 품질 점수와 이력

----
점수 = 통과 규칙 수 / 평가된 규칙 수 × 100%
       (평가된 규칙 = 이번에 판정한 규칙 + 직전 결과를 이어받은 규칙, 미평가 제외)
----

* 미평가 규칙은 분모에서 빠지므로 점수를 올리지도 내리지도 않습니다. 화면의 *전체 N개* 도 평가된 규칙 수입니다.
* 평가된 규칙이 하나도 없으면 점수를 내지 않습니다 — 진단한 적이 없는 데이터셋처럼 품질 점수가 `—` 로 보이고 품질 상태도 비어 있습니다.
* 점수에 따라 데이터셋의 품질 상태가 자동으로 바뀌고, 데이터셋 목록 · 상세와 <<_업스트림_품질_경고,업스트림 품질 경고>> 에 쓰입니다.
+
[cols="1,3"]
|===
| 상태 | 조건

| *BAD* | 치명(BREAKING) 실패가 있거나 점수 70% 미만
| *WARN* | 그 밖에 실패가 있거나 점수 90% 미만
| *GOOD* | 모두 통과
|===
* 실패가 있으면 xref:governance/alerts.adoc[알림] 의 품질 실패 규칙이 평가되어 구독자에게 알림이 갑니다.
* 진단할 때마다 점수 이력이 쌓이며, 점수 영역의 추세선이 최근 20회까지 보여 줍니다.

[[_진단_주기]]
== 진단 주기

정해진 주기로 진단하려면 관리 › 데이터 품질의 <<help-quality-jobs,품질 진단 작업>> 에 이 데이터셋을 대상으로 작업을 등록하고
주기(매시간 · 매일 · 매주 · 매월)를 정합니다. 작업 하나가 데이터셋 하나를 진단합니다. 품질 탭 점수 영역의 *주기 진단 설정 →* 이 그 화면으로 갑니다 —
이 링크는 관리 › 데이터 품질을 열 수 있는 관리자와 데이터 품질 관리(`quality.manage`)를 위임받은 사람에게만 보입니다.
작업은 주기마다 대상 데이터셋의 정밀 진단을 대기열에 넣습니다.

[NOTE]
.예전 데이터셋 진단 주기
====
예전 품질 탭의 *주기*(매시간 · 매일 · 매주 — 간이 진단을 자동 실행)는 없앴습니다. 정해 둔 주기는 카탈로그 서버가 업데이트 뒤 처음 기동할 때
그 데이터셋 하나를 대상으로 하는 품질 진단 작업 *<데이터셋 이름> 주기 진단* 으로 옮깁니다 — 매시간은 1시간마다, 매일은 03:00, 매주는 월요일 03:00
(Asia/Seoul). 시각이 맞지 않으면 작업을 열어 고치세요. 옮긴 작업은 간이 진단이 아니라 정밀 진단을 돌립니다.
====

[[_업스트림_품질_경고]]
== 업스트림 품질 경고

xref:catalog/lineage.adoc[리니지] 상 이 데이터셋의 원천 중 품질 상태가 *WARN* 또는 *BAD* 인 데이터셋이 있으면, 품질 탭 맨 위에
*업스트림 품질 경고* 배너가 나타납니다. 원천 데이터셋 이름을 누르면 그 데이터셋으로 이동하고, 옆 배지에 상태(WARN 은 *주의*, BAD 는 *불량*)와 점수(예: `주의 75%`)가 보입니다.
점수는 그 데이터셋 품질 탭의 품질 점수와 같은 값(소수 한 자리, 예: `불량 33.3%`)입니다.
파생 데이터의 품질 문제가 원천에서 왔는지 먼저 확인할 때 씁니다.

image::catalog-quality/upstream-warning.png[업스트림 품질 경고 — 원천 데이터셋 이름과 상태 · 점수 배지, 900]

== 정밀 진단 [[help-quality-trino]]

*정밀 진단*(이전 이름 _Trino 진단_)은 테이블 *전체 데이터* 를 읽어 규칙을 평가합니다(예전의 프로파일 통계로 판정하던 *간이 진단* 은 없앴습니다).
규칙마다 *진단 건수* 와 *오류 건수* 를 남겨 *오류율*(오류 건수 ÷ 진단 건수)을 보여 줍니다.

진단은 카탈로그 서버가 실행하지 않습니다. 카탈로그는 실행을 대기열에 넣고 진행을 보여 주며, 별도 서비스인 *품질 워커* 가 대기열에서 실행을 가져가
처리합니다. 데이터셋마다 경로가 정해집니다.

[cols="1,3,3",options="header"]
|===
| 경로 | 언제 | 어떻게

| *Trino* | 데이터셋의 카탈로그에 Trino 데이터 소스가 *카탈로그 연결*(QUERY)로 이어져 있을 때 | 품질 워커가 Trino 에 집계 쿼리를 냅니다. 원본 DB 에는 Trino 가 접속하므로 원본 접속 정보는 Trino 카탈로그에만 있으면 됩니다.
| *원천 직접* | Trino 연결이 없고 원본이 PostgreSQL · MySQL · MariaDB · Oracle · SQL Server 일 때 | 품질 워커가 원본 DB 에 직접 접속합니다(읽기 전용 트랜잭션 — SQL Server 는 읽기 전용 트랜잭션이 없어 읽기 권한만 있는 계정을 씁니다). DB 마다 뜻이 같은 규칙은 원본이 집계 쿼리 하나로 세고, 값의 모양을 보는 규칙만 필요한 컬럼을 한 번 읽어 워커가 평가합니다(아래). 접속 정보는 원본 데이터 소스의 접속 설정을 씁니다.
|===

두 경로의 판정 기준은 같습니다 — 같은 규칙이면 어느 경로로 진단해도 진단 건수 · 오류 건수가 같습니다. 다만 경로마다 평가하는 유형이 조금 다릅니다.

[cols="2,1,1,3",options="header"]
|===
| 유형 | Trino | 원천 직접 | 비고

| 기본 유형(NULL 없음 · 고유값 · 하한 · 상한 · 행 수 · 허용 값 · 정규식 · 날짜 형식 · 컬럼 간 비교 · 글자 깨짐 · 공백 · 논리관계 · 계산식) | ✓ | ✓ |
| Trino 함수 (`FUNCTION`) | ✓ | — | Trino 에 등록한 함수를 부릅니다
| 더미 값 (`DUMMY_VALUE`) · 데이터 연속성 (`CONTINUITY`) | ✓ | ✓ | AI-Ready 품질 지표(<<_ai_ready_품질_지표,아래>>). 연속성은 날짜 · 시각 타입 컬럼이나 형식을 적은 문자열 날짜만 — 주(`WEEK`) 단위의 문자열 날짜는 Trino 경로만
| 값 분포 다양성 (`DIVERSITY`) · 여러 컬럼 키 고유값 (`COMPOSITE_UNIQUE`) | ✓ | ✓ | AI-Ready 품질 지표. 값(키)마다 행 수를 세어 다시 집계하는 쿼리를 규칙마다 하나 냅니다
| 참조관계 (`REFERENTIAL`) | ✓ | ✓ | Trino: 참조 데이터셋도 같은 Trino 로 읽을 수 있어야 함. 원천 직접: 참조 데이터셋이 *같은 원본 데이터 소스* 에 있어야 함(원본에 조인 쿼리 하나)
| 커스텀 SQL (`CUSTOM_SQL`) | ✓ | — | Trino 에서 실행. 테이블 이름만 적으면(`FROM rental`) 이 데이터셋의 Trino 카탈로그 · 스키마에서 찾습니다
| 커스텀 Python (`CUSTOM_PYTHON`) | (✓) | ✓ | 품질 워커가 읽은 행(스키마의 모든 컬럼)의 pandas DataFrame 으로 플러그인을 부릅니다. Trino 경로라도 원본이 PostgreSQL · MySQL · MariaDB · Oracle · SQL Server 이면 같은 실행에서 원본을 따로 읽어 평가합니다(아래)
| 최신성 (`FRESHNESS`) | ✓ | ✓ | 시각 컬럼의 최댓값만 구하고 경과 시간은 워커가 결과를 받은 시각으로 계산합니다
|===

경로가 평가하지 않는 규칙은 건너뛰고(직전 결과를 이어받고, 실행의 사유에 건너뛴 규칙이 나옵니다), 품질 탭의 규칙 목록에 *정밀 진단 제외* 가
붙습니다. 규칙 추가 대화상자에서도 그런 유형을 고르면 안내가 나옵니다. 커스텀 SQL · 커스텀 Python 은 관리지침 진단 기준 밖이라 진단 기준(품질 지표)을
고르지 않은 진단에서만 평가합니다.

Trino 로 진단하는 데이터셋도 원본이 PostgreSQL · MySQL · MariaDB · Oracle · SQL Server 이고 원본 데이터 소스에 접속 설정이 있으면, 커스텀 Python 규칙은 같은 실행에서 품질 워커가
원본을 직접 읽어 평가합니다 — 다른 규칙은 Trino 로, 커스텀 Python 만 원본으로 갑니다(실행 이름 _품질 진단 (Trino + 원천 직접)_).
원본을 읽지 못하면 커스텀 Python 규칙만 건너뛰고(직전 결과 유지) 실행의 사유에 그 이유가 나옵니다.

원천 직접 경로는 규칙을 두 방식으로 나눠 평가합니다.

[cols="1,2,3",options="header"]
|===
| 방식 | 규칙 | 동작

| 원본 집계
| 행 수 · NULL 없음 · 고유값 · 하한/상한(숫자 컬럼) · 허용 값(문자열 · 정수 컬럼) · 컬럼 간 비교(같은 종류의 두 컬럼) · 날짜 형식(날짜 · 시각 타입 컬럼) · 더미 값(문자열 · 숫자 컬럼) · 데이터 연속성
| 원본 DB 가 집계 쿼리 하나로 세고 결과 한 행만 받습니다. 테이블이 커도 전체를 평가하고, 데이터셋의 행 수도 이 쿼리로 갱신합니다.
  문자열은 Trino 경로처럼 대소문자 · 끝 공백을 구분해 비교합니다(MySQL · MariaDB 의 기본 정렬 규칙과 다름). 묶은 쿼리가 실패하면 규칙별로 다시 냅니다.
| 묶음 집계
| 값 분포 다양성 · 여러 컬럼 키 고유값
| 원본 DB 가 값(키 묶음)마다 행 수를 세어 다시 집계하는 쿼리를 규칙마다 하나 내고 결과 한 행만 받습니다. 다섯 원본 유형 모두 원본에서 셉니다.
  같은 값으로 묶는 기준은 Trino 경로처럼 대소문자 · 끝 공백을 구분합니다 — MySQL · MariaDB · SQL Server 문자열은 값의 바이트로 묶고
  (기본 정렬 규칙이 대소문자 · 끝 공백을 무시하므로), PostgreSQL · Oracle 은 DB 의 비교(바이트 비교)로 묶습니다.
| 행 읽기
| 정규식 · 날짜 형식(문자열 컬럼) · 글자 깨짐 · 공백 · 논리관계 · 계산식 · 커스텀 Python, 그리고 위 규칙 가운데 타입이 맞지 않는 것(실수 · 날짜의 허용 값 · 더미 값, 문자열의 하한/상한, 종류가 다른 컬럼 비교, JSON · 배열 · 이진 컬럼의 고유값)
| 규칙이 쓰는 컬럼만 원본에서 읽어 품질 워커가 평가합니다. 정규식 문법 · 날짜 함수가 DB 마다 달라 판정을 워커 한곳에서 합니다.
  한 실행이 읽는 행은 품질 워커의 `direct.max_rows`(기본 500만 행)까지이며, 넘으면 앞부분만 평가하고 결과 설명과 실행의 사유에 그 사실을 적습니다.
|===

=== 준비 (Trino 경로)

. Trino 에 이 원본을 읽는 카탈로그가 있어야 합니다.
. 카탈로그에 그 Trino 를 *Trino 데이터 소스* 로 등록하고 접속 설정을 저장합니다.
. Trino 데이터 소스의 *카탈로그 연결* 에서 이 데이터셋이 속한 카탈로그를 역할 *QUERY* 로 연결하고, *원격 이름* 에 Trino 카탈로그 이름을 적습니다.
. 품질 워커를 실행합니다(관리자 — 설치 · 실행은 운영 문서의 `argus-catalog-quality-worker`).

Trino 연결이 없는 PostgreSQL · MySQL · MariaDB · Oracle · SQL Server 데이터셋은 따로 준비할 것 없이 원천 직접 경로로 진단합니다 — 원본 데이터 소스의
접속 설정(호스트 · 포트 · 데이터베이스 · 계정)과, 품질 워커가 원본 DB 에 닿을 수 있는 네트워크만 있으면 됩니다. 읽기 권한만 있는 계정이면 충분합니다.

Oracle · SQL Server 는 다음이 다릅니다.

* 품질 워커에 드라이버를 더 설치합니다 — Oracle 은 python-oracledb(Oracle Client 없이 동작), SQL Server 는 pymssql(품질 워커 README).
* Oracle 은 12c 이상, 접속 설정의 Service Name(없으면 SID)으로 접속합니다.
* SQL Server 는 데이터셋이 있는 데이터베이스(`<데이터베이스>.<스키마>.<테이블>`)에 접속합니다. 읽기 전용 트랜잭션이 없으므로 *읽기 권한만 있는 계정*(예: `db_datareader`)을 쓰세요.
* SSL: 데이터 소스 접속 설정의 SSL(`ssl_enabled`)이 켜져 있으면 암호화 접속을 합니다 — PostgreSQL(`sslmode=require`) · MySQL 과
  같은 수준으로 암호화만 강제하고 서버 인증서는 검증하지 않습니다. 서버가 TLS 를 못 하면 평문으로 내려가지 않고 접속이 실패합니다.
** Oracle 은 TCPS 로 접속합니다(지갑 없이 — python-oracledb thin). 접속 설정의 포트를 TCPS 리스너 포트(보통 2484)로 적으세요.
** SQL Server 는 pymssql 의 `encryption=require` 로 로그인부터 암호화합니다(서버의 자체 서명 인증서도 됩니다).
** 데이터 소스 화면의 Oracle · SQL Server 폼에는 아직 *SSL Enabled* 항목이 없습니다 — 메타데이터 수집 · 연결 테스트(Metadata Sync)가
   이 설정을 쓰지 않기 때문입니다. 품질 진단만 암호화하려면 데이터 소스 API 로 접속 설정에 `"ssl_enabled": true` 를 넣습니다.
* 원본 집계는 행 수 · NULL 없음 · 최신성 · 데이터 연속성만 원본에서 세고(값 분포 다양성 · 여러 컬럼 키 고유값은 묶음 집계로 원본에서 셈), 나머지 규칙은 행을 읽어 워커가 평가합니다(행 수 상한 `direct.max_rows`).
  참조관계는 참조 데이터셋이 같은 원본 데이터 소스(SQL Server 는 같은 데이터베이스)에 있어야 합니다.
* DB 의 성질 때문에 다른 원본과 결과가 다를 수 있는 곳:
** Oracle 은 빈 문자열(`''`)을 NULL 로 저장합니다 — 다른 DB 에서 빈 문자열이던 값은 NULL 없음 · 고유값 등에서 NULL 로 셉니다.
** Oracle `DATE` 는 시각까지 담습니다 — 프로파일 · 위반 샘플의 날짜 값이 `2024-01-01 00:00:00` 처럼 보입니다(건수는 같음).
** Oracle `TIMESTAMP WITH TIME ZONE` 은 python-oracledb thin 이 시간대를 떼고 그 값의 현지 시각으로 돌려줍니다(최신성은 원천 데이터 시간대로
   해석). 값이 지역 이름 시간대(`Asia/Seoul` 등)로 저장돼 있으면 thin 모드가 읽지 못해(`DPY-3022`) 그 컬럼을 읽는 규칙 · 프로파일이 실패합니다 —
   이런 테이블은 Trino 연결로 진단하세요.
** Oracle 에서 방금 만들거나 다시 만든(DDL) 테이블은 몇 초 동안 읽기 전용 트랜잭션에서 `ORA-01466` 으로 읽히지 않습니다 — 그 실행은
   진단하지 못한 것으로 남고(직전 결과 유지) 다음 실행에서 진단됩니다.
** 프로파일: Oracle LOB(`CLOB` · `NCLOB` · `BLOB`)은 NULL 수만 셉니다. SQL Server 의 `TEXT` · `NTEXT` · `IMAGE` 는 `(MAX)` 타입으로,
   `XML` 은 NULL 수만, `BIT` 는 0 · 1 로 셉니다.
** 참조관계 조인의 문자열 비교는 원본 DB 의 정렬 규칙을 따릅니다 — MySQL · MariaDB · SQL Server 의 기본 정렬 규칙은 대소문자 · 끝 공백을
   무시하므로 `abc` 와 `ABC` 를 같은 값으로 봅니다(Trino 경로는 다른 값).

진단할 수 있으면 품질 탭 점수 영역의 *정밀 진단* 버튼을 누를 수 있고, 마우스를 올리면 경로와 대상 테이블이 나옵니다. 진단할 수 없으면
버튼이 흐리게 보이고, 마우스를 올리면 그 이유(연결이 없고 원천 직접을 지원하지 않는 유형, 진단에 쓸 데이터 소스에 접속 설정이 없음,
활성 규칙이 없음 등)가 나옵니다.

=== 실행

*정밀 진단* 을 누르면 실행이 대기열에 들어가고 품질 점수 영역 바로 아래에 상태 카드가 나타납니다. 상태는 *대기 중 → 실행 중 → 완료 / 일부 실패 / 실패 / 중지됨* 으로 바뀝니다.
실행 중에는 카드에 돌아가는 표시와 진행 막대(쿼리 진행 수), 지금 실행 중인 쿼리, 대기 · 실행 경과 시간이 나오고 3초마다 새로 고칩니다.

* 같은 테이블의 컬럼 규칙은 한 번의 읽기(쿼리 하나)로 묶어 평가합니다. 묶은 쿼리가 실패하면 규칙마다 따로 실행해 문제 규칙만 실패로 남깁니다(*일부 실패*).
* 모든 쿼리가 실패하면(Trino · 원본 접속, 권한, 테이블 이름 문제) 결과를 남기지 않고 *실패* 로 끝납니다.
* 쿼리 실패는 원인에 따라 다르게 남습니다. 규칙이 잘못된 경우(없는 컬럼 · 틀린 정규식 · 타입이 맞지 않는 비교)는 그 규칙을 *실패* 로
  저장합니다. Trino 의 시간 초과 · 자원 부족 · 내부 오류처럼 규칙의 잘못이 아닌 경우는 결과를 남기지 않고 직전 결과를 그대로 두며,
  실행의 사유에 _진단하지 못한 규칙_ 으로 적습니다 — 품질 점수와 알림이 일시적인 장애로 흔들리지 않습니다.
* 대기 · 실행 중에는 카드의 *정밀 진단 중지*(프로파일은 *프로파일 중지*)로 멈출 수 있습니다. 대기 중이면 바로 멈추고, 실행 중이면 확인 창의 *중지* 를 누른 뒤
  카드가 *중지 중* 으로 바뀌고 품질 워커가 다음 확인 때 멈춥니다 — Trino 쿼리도 함께 취소되고, 원천 직접 경로는 읽던 묶음을 마친 뒤 읽기를 멈추고
  원본과의 연결을 끊습니다. 원본 집계 · 프로파일처럼 결과 한 행을 기다리는 쿼리는 원본에서 바로 멈춥니다(PostgreSQL 취소 요청,
  MySQL · MariaDB `KILL QUERY`). 중지한 실행은 결과를 남기지 않고 직전 결과가 그대로 유지됩니다.
* 한 원본 데이터 소스에는 진단이 동시에 하나만 실행됩니다. 나머지는 대기합니다.
* 살아 있는 품질 워커가 없으면 *정밀 진단* 을 누를 때 확인 창으로 먼저 알립니다. 요청하면 실행이 대기 상태로 남고 상태 카드에 안내가 나옵니다 —
  관리자에게는 워커를 띄우라는 안내, 다른 사용자에게는 관리자에게 문의하라는 안내입니다. 워커가 없는 채 1시간이 지나면 그 실행은 *실패* 로 끝납니다.

=== 관리지침 진단 기준 유형

공공데이터 관리지침의 진단 기준과 AI-Ready 품질 지표를 위한 유형입니다. 예전 간이 진단 · 품질 배치는 평가하지 않던 유형입니다.

[cols="2,3,3",options="header"]
|===
| 유형 (화면 이름) | 기대값 | 통과 조건

| `DATE_FORMAT` (날짜 형식) | 날짜 형식 — 목록에서 고르거나 직접 적음. 예: `YYYYMMDD`, `YYYY/MM/DD`, `YYYY.MM.DD HH24:MI` | 값이 그 형식의 자릿수 · 구분자와 같고 달력 · 시각에 있는 값(2월 30일 · 13월 · 24시는 오류). 날짜 · 시각 타입 컬럼은 항상 통과
| `COLUMN_COMPARE` (컬럼 간 비교) | `<연산자> <다른 컬럼>` — 예: `\<= end_ymd` | 두 컬럼이 모두 있는 행에서 비교가 참
| `REFERENTIAL` (참조관계) | `<부모 데이터셋 URN 또는 ID>#<부모 컬럼>` | 값이 부모 테이블의 그 컬럼에 있음. 부모가 다른 원본이어도 같은 Trino 에 연결돼 있으면 됩니다(Trino 경로만)
| `BROKEN_TEXT` (글자 깨짐) | 쓰지 않음 | 값에 대체 문자(U+FFFD)나 낱자만 있는 한글(ㄱ · ㅏ 등)이 없음
| `WHITESPACE` (공백 · 특수문자) | (선택) 쓰면 안 되는 문자를 이어 적음 — 예: `#$%` | 값 앞뒤에 공백(전각 공백 포함)이 없고 값 안에 제어 문자(탭 · 줄바꿈)와 금지 문자가 없음
| `LOGICAL` (논리관계) | `IF <조건> THEN <조건>` — 예: `IF cancel_yn = 'Y' THEN cancel_ymd IS NOT NULL`. 컬럼은 고르지 않음 | 앞 조건이 참인 행에서 뒤 조건도 참. 진단 건수는 앞 조건이 참인 행 수
| `FORMULA` (계산식) | 컬럼 이름 · 숫자 · 사칙연산 · 괄호로 쓴 식 — 예: `supply_amt + vat_amt`. 끝에 `~ 0.01` 로 허용 오차 | 이 컬럼의 값이 식의 결과와 같음(어느 한쪽이 NULL 인 행은 세지 않음)
| `DUMMY_VALUE` (더미 값) | (선택) 더미 값을 하나씩 배지로 — 예: `999999` · `-999` · `N/A`. 비우면 흔한 자리채움 값(`999999` · `-999` · `-9999` · `N/A` · `NA` · `NULL` · `-` · `없음` · `미상` · `0000-00-00` 등) | 더미 값이 아닌 값의 비율이 *임계값(%)* 이상(100 = 하나도 없어야 함). 숫자 컬럼은 숫자 더미 값만 비교합니다(`999999.0` 도 같은 값). 문자열은 값 전체가 같아야 하고 대소문자를 가립니다
| `CONTINUITY` (데이터 연속성) | 기간 단위 `HOUR` · `DAY` · `WEEK` · `MONTH` · `YEAR`. 문자열로 저장한 날짜면 뒤에 형식 — 예: `DAY`, `WEEK`, `MONTH`, `DAY YYYYMMDD`, `MONTH YYYY-MM` | 가장 이른 기간부터 가장 늦은 기간까지 값이 있는 기간의 비율이 *임계값(%)* 이상(100 = 빠진 기간이 없어야 함). 진단 건수는 그 사이의 기간 수, 오류 건수는 값이 하나도 없는 기간 수
| `DIVERSITY` (값 분포 다양성) | (선택) 가장 많은 값의 비율 상한(%) — 예: `80`. 비우면 `90` | 값마다 행 수를 세어, 가장 많은 값의 행 수 ÷ 진단 건수(NULL 제외)가 상한 이하. 진단 건수는 NULL 이 아닌 행 수, 오류 건수는 상한을 넘친 최빈값 행 수(그만큼 줄어야 상한 안에 듦). 판정 설명에 고유값 수와 최다/최소 빈도 비율도 나옵니다
| `COMPOSITE_UNIQUE` (여러 컬럼 키 고유값) | 키 컬럼을 둘 이상 — 대화상자에서 컬럼 이름을 눌러 고릅니다(고른 순서대로). 컬럼 칸은 쓰지 않음(테이블 수준) | 키 묶음이 겹치지 않는 행의 비율이 *임계값(%)* 이상(100 = 겹치는 키가 없어야 함). 키가 겹치는 행은 모두 오류 건수로 셉니다(같은 키가 3행이면 3건). 키 컬럼 가운데 하나라도 NULL 인 행은 진단하지 않습니다(DB 의 UNIQUE 제약과 같음)
|===

더미 값 · 데이터 연속성 · 여러 컬럼 키 고유값은 다른 정밀 진단 유형과 달리 *임계값(%)* 을 씁니다 — 원천 데이터에 결측 표기가 조금 섞이는 것을 허용하려면
`99` 처럼 낮춥니다. 데이터 연속성의 문자열 날짜 형식은 연 → 월 → 일 → 시 순서여야 하고(`DD/MM/YYYY` 는 안 됨), 단위까지의 앞부분으로 기간을
묶습니다(`MONTH YYYYMMDD` 는 앞 6자리). 형식과 모양이 다른 값은 세지 않습니다 — Trino 경로는 숫자 자리까지, 원천 직접 경로는 자릿수와
구분자만 봅니다(`2024-01-05` 는 `YYYYMMDD` 에서 빠지지만 `2024AB05` 는 들어감). 그래서 형식이 틀린 값은 *날짜 형식* 규칙으로 따로 진단하세요 —
가장 이른 · 늦은 값을 날짜로 읽을 수 없으면 연속성 규칙은 *실패* 로 저장됩니다.

주(`WEEK`) 단위는 *월요일에 시작하는 ISO 8601 주* 입니다 — 일요일은 앞 월요일의 주에 듭니다. 날짜 · 시각 컬럼을 그 주의 월요일로 잘라 묶고(Trino ·
PostgreSQL `date_trunc('week', …)`, Oracle `TRUNC(…, 'IW')`, MySQL · MariaDB `WEEKDAY`, SQL Server 기준일 1900-01-01(월요일)부터의 날 수 — `DATEFIRST`
설정과 상관없음), 연도가 바뀌는 주도 한 주로 셉니다. 문자열 날짜는 형식에 일(`DD`)까지 있어야 하고(`WEEK YYYYMMDD`), Trino 경로에서만 됩니다 —
원천 직접 경로는 날짜 · 시각 타입 컬럼만 봅니다.

값 분포 다양성은 범주 · 라벨 컬럼(성별 · 지역 · 등급 · 분류 라벨)이 한 값으로 쏠렸는지 봅니다. 가이드라인은 '최다/최소 클래스 비율' 을 예로 들지만,
판정은 *가장 많은 값의 비율* 로 합니다 — 최다/최소 비율은 오타 같은 드문 값 하나(1건)에 크게 흔들리고 값 종류가 많은 컬럼은 늘 실패하기 때문입니다.
최다/최소 비율은 판정 설명에 참고로 적습니다. 기본 상한 90% 는 나머지 값을 모두 합쳐 10% 가 안 될 만큼 심하게 쏠린 경우만 잡습니다. 두 값(Y/N) 라벨을
고르게 하려면 `70` 처럼 낮추고, 값이 많은 컬럼일수록 낮게 잡습니다. NULL 은 세지 않으니 결측은 필수값 규칙으로 따로 봅니다.

[[_표준_코드_그룹을_허용_값으로]]
==== 표준 코드 그룹을 허용 값으로

허용 값 목록(`ACCEPTED_VALUES`) 규칙은 값을 직접 넣는 대신 데이터 표준(거버넌스 › 데이터 표준)의 *코드 그룹* 을 가리킬 수 있습니다(AI-Ready
*기준 정합성* — 표준 코드표와 대조). 규칙 추가 대화상자의 기대값 칸에서 *데이터 표준의 코드 그룹 쓰기* 를 고르고 코드 그룹을 고릅니다. 선택지에
사전 이름, 사용 중인 코드 값 수와 앞의 값 몇 개가 나옵니다.

* 허용 값은 *진단을 요청할 때* 그 그룹의 사용 중인 코드 값(사용 여부가 꺼진 값은 뺌)으로 풀어 실행에 남깁니다 — 코드 값을 고치면 다음 진단부터
  반영되고, 이미 끝난 실행의 결과는 그때의 값 그대로입니다. 진단 쿼리 보기 · 품질 지표의 미리보기도 지금의 코드 값으로 보여 줍니다.
* 비교하는 것은 코드 값(예: `M` · `F`)입니다. 코드 이름(남성 · 여성)은 보지 않습니다.
* 코드 그룹을 지우거나 사용 중인 코드 값이 하나도 없으면 그 규칙은 *표준 코드 그룹 #N 의 코드 값을 읽지 못했습니다* 로 *실패* 합니다.
* 규칙 목록에는 *코드 그룹: <사전> › <그룹>* 으로 보입니다. API 로는 기대값에 `{"code_group_id": <코드 그룹 번호>}` 를 적고, 고를 수 있는 그룹은
  `GET /api/v1/quality/code-groups` 로 봅니다.

[[_ai_ready_품질_지표]]
=== AI-Ready 품질 지표

「공공데이터의 인공지능 친화적 관리 가이드라인」(행정안전부 · NIA, 2026) 은 AI 학습에 쓰는 데이터의 품질을 *완전성 · 일관성 · 정확성 · 적시성 ·
유효성 · 유일성* 6개 지표로 봅니다. 카탈로그는 관리지침의 진단 기준을 그대로 쓰면서 각 진단 기준을 AI-Ready 지표와 세부 지표에 맞춰 두었고,
리포트에서 같은 결과를 이 6개 지표로 묶어 볼 수 있습니다(<<help-quality-report,리포트>>). 관리지침에 없는 *더미 값* · *데이터 연속성* ·
*값 분포 다양성* · *여러 컬럼 키 중복* 은 AI-Ready 를 위해 더한 진단 기준입니다(영역은 기타).

[cols="1,2,3",options="header"]
|===
| AI-Ready 지표 | 세부 지표 | 진단 기준(관리지침)

| 완전성 | 필수 속성 충족도 | 필수값
| 완전성 | 데이터 · 라벨 다양성 | *값 분포 다양성*(새 기준)
| 일관성 | 관계 일관성 | 시간순서 · 선후관계 · 논리관계
| 일관성 | 참조 무결성 | 참조관계
| 정확성 | 기준 정합성 | 여부 · 코드 — 허용 값을 표준 코드 그룹으로 정할 수 있음
| 정확성 | 규칙 정확성 | 계산식
| 적시성 | 데이터 연속성 | *데이터 연속성*(새 기준)
| 유효성 | 형식 유효성 | 글자 깨짐 · 공백·특수문자 · 날짜 · 번호 · 문자열 형식
| 유효성 | 수치 범위 유효성 | 금액 · 수량 · 율
| 유효성 | 통계적 타당성 | *더미 값*(새 기준)
| 유일성 | 데이터 유일성 | 중복데이터 · *여러 컬럼 키 중복*(새 기준)
|===

건수(행 수 하한)는 AI-Ready 지표에 들지 않습니다. 적시성의 다른 세부 지표(갱신 주기 준수)는 데이터셋 AI-Ready 탭의 체크리스트가 봅니다.

날짜 형식은 낱말 `YYYY` `MM` `DD` `HH24`(`HH` 도 같음) `MI` `SS` `SSS`(밀리초 3자리) 와 구분자 `-` `/` `.` `:` 공백 `T` 를 이어 적습니다. 순서는 자유이고
같은 낱말은 한 번만 씁니다 — `DD/MM/YYYY`, `YYYY-MM-DDTHH24:MI:SS`, `HH24MISS` 모두 됩니다. 시 바로 뒤의 `MM` 은 분으로 읽으므로
`YYYY-MM-DD HH:MM:SS`, `YYYY-MM-DD HH:MM:SS.SSS` 처럼 적어도 됩니다. 규칙 대화상자의 선택 상자에는 흔한 형식 13가지가
값 예와 함께 나오고, *직접 입력…* 을 고르면 다른 조합을 적을 수 있습니다. 일이 없는 형식(`YYYYMM`)은 달만, 연도만 있는 형식(`YYYY`)은
자릿수만 봅니다. 두 자리 연도(`YY`)와 영문 월 이름은 받지 않습니다.

논리관계의 조건은 정해진 모양만 받습니다: `컬럼 연산자 값(또는 컬럼)`, `컬럼 IS [NOT] NULL`, `컬럼 [NOT] IN (값, …)` 을 `AND` · `OR` 로 잇습니다
(괄호로 묶을 수 없습니다). 값은 작은따옴표 문자열, 숫자, 날짜 · 시각 상수(`DATE '2024-01-31'` · `TIMESTAMP '2024-01-31 09:00:00'`)입니다.
문자열 값은 문자열 컬럼하고만, 숫자는 숫자 컬럼하고만, 날짜 · 시각 상수는 날짜 · 시각 컬럼하고만 비교합니다 — 예: `IF paid_yn = 'Y' THEN paid_at >= DATE '2024-01-01'`.
날짜 · 시각 타입 컬럼을 `'2024-01-01'` 같은 문자열과 비교하면 그 규칙은 *실패* 로 저장됩니다. 없는 날짜(`DATE '2024-02-30'`)는 저장할 때 알려 줍니다.
시간대가 있는 컬럼(`timestamptz` 등)과 비교하면 상수를 UTC 시각으로 봅니다. 논리관계와 계산식은 저장할 때 모양이 틀리면 바로 알려 주고,
컬럼이 실제로 있는지는 진단할 때 확인합니다.

NULL 은 위 3종과 허용 값 · 정규식에서 오류로 세지 않습니다. NULL 은 `NOT_NULL` 규칙이 봅니다.

[[_데이터_품질_화면]]
== 관리 메뉴의 데이터 품질 화면 [[help-quality-runs]]

*관리 → 데이터 품질* 은 다섯 탭으로 나뉩니다. *실행 현황* 은 모든 데이터셋의 정밀 진단 실행을, *품질 지표* 는 미리 정해 컬럼에 할당하는 진단 기준을, *품질 진단 작업* 은 주기적으로 돌리는 진단의 정의를, *작업 이력* 은 품질 진단 작업이 돈 기록을, *리포트* 는 작업 실행의 요약과 추이를 봅니다.

=== 실행 현황

*실행 현황* 탭은 모든 데이터셋의 정밀 진단 실행을 한곳에서 봅니다. 관리자와 *데이터 품질 관리* (`quality.manage`) 기능 권한을 받은 역할에 메뉴가 보입니다.
이 메뉴의 화면이 쓰는 기능(작업 · 작업 이력 · 리포트 · 실행 현황)도 같은 조건입니다 — *데이터 품질 관리* 는 명시 허용형이라 아무 역할에도 주지
않았으면 관리자만 씁니다. 데이터셋 품질 탭의 *품질 진단 실행* (`quality.run`) 과는 따로 정합니다. 품질 진단 작업에 주기를 두려면 *진단 주기 설정* (`quality.schedule`) 도 필요합니다.

* 맨 위에 품질 워커 상태가 나옵니다 — 살아 있는 워커 수, 실행 중 · 대기 중인 작업 수. 워커가 없으면 빨간 점과 안내가 나옵니다.
* *상태*(실행 중·대기 / 실패·일부 실패 / 완료 / 중지됨 / 전체), *데이터 소스*(진단 대상의 원본), *기간* 으로 좁힙니다. 조건은 주소에 남습니다.
* 행마다 데이터셋, 요청자와 시작 시각, 진행(끝난 쿼리 수 · 지금 실행 중인 쿼리), 경과 시간, 평가한 규칙 수, 진단 · 오류 건수, 오류율이 나옵니다.
* 데이터셋 이름을 누르면 그 데이터셋의 품질 탭으로 갑니다.
* 행을 누르면 상세가 열립니다. 탭 세 개로 나뉩니다.
** *개요* — 대상(원본 데이터 소스·엔진(Trino 또는 원천 직접)·진단한 테이블), 실행 방식·요청자·처리한 워커, 접수·시작·종료 시각과 소요 시간, 규칙 수·진단/오류 건수·오류율, 품질 점수(막대), 오류 내용.
** *규칙별 결과* — 이 실행에서 평가한 규칙마다 통과 여부·진단/오류 건수·오류율.
** *Trino 쿼리*(원천 직접 경로는 *원천 쿼리*) — 품질 워커가 Trino 에서 실행한 진단 쿼리(SQL)와 쿼리 ID. 원천 직접 경로는 원본에 낸 집계 쿼리 · 읽기 쿼리 · 참조관계 쿼리가 나옵니다. 같은 테이블의 규칙은 스캔 쿼리 하나로 묶이고, 식마다 어느 규칙의 것인지 주석이 붙습니다. 묶은 쿼리가 실패해 규칙별로 다시 실행했으면 그 쿼리들도 "규칙별 재실행" 으로 나옵니다. 쿼리 ID 로 Trino UI 에서 쿼리 계획을 찾을 수 있습니다.
  끝난 실행은 *규칙별 결과*(규칙 · 진단 기준 · 통과 여부 · 진단 건수 · 오류 건수 · 오류율)도 함께 나옵니다 — 그 실행에서 실제로 평가한 규칙만입니다.
* 실행 중 · 대기 중인 작업은 *중지*(*품질 진단 실행* 권한), 끝난 작업은 *다시 실행*(*데이터 품질 관리* 권한)으로 같은 데이터셋을 다시 진단합니다.
  다시 실행은 원래 실행과 같은 종류(프로파일은 프로파일, 진단은 진단)와 같은 범위(작업이 고른 품질 지표 · 진단 기준)로 돕니다.
* 실행 중인데 워커 보고가 2분 넘게 없으면 *워커 응답 없음* 으로 표시하고, 5분이 지나면 실패로 정리합니다.

* 품질 진단 작업이 넣은 실행은 시작 칸에 *배치: 작업 이름* 이 함께 나옵니다.

[[help-quality-definitions]]
=== 품질 지표

*품질 지표* 탭에서는 진단 기준을 지표로 한 번 정해 두고 여러 컬럼에 할당합니다. "여부 컬럼은 Y/N", "날짜는 YYYYMMDD", "금액은 0 이상"
같은 기준을 데이터셋마다 규칙으로 다시 적지 않아도 되고, 기준이 바뀌면 지표 하나만 고치면 됩니다.

image::catalog-quality/definitions.png[관리 › 데이터 품질 › 품질 지표 탭 — 지표 목록(진단 기준 · 통과 조건 · 심각도 · 할당), 900]

image::catalog-quality/definition-add.png[품질 지표 추가 — 진단 기준 코드 · 허용 값과 진단 쿼리 (Trino) 미리보기, 900]

. *기본 지표 추가* 를 누르면 흔한 지표(필수값 · 중복 없음 · 날짜 YYYYMMDD · 여부 Y/N · 금액 0 이상 · 전화번호 등) 가운데 아직 없는 것이 들어갑니다.
  이미 같은 이름이 있는 지표는 건드리지 않습니다.
. *지표 추가* 로 직접 만듭니다. 이름, *진단 기준*(날짜 · 번호 · 여부 · 코드 · 금액 · 수량 · 율 · 필수값 · 중복데이터 · 글자 깨짐 · 공백·특수문자 · 더미 값 · 데이터 연속성 · 값 분포 다양성),
  기준값(날짜 형식 · 허용 값 · 하한/상한 · 정규식 · 더미 값 · 기간 단위 · 가장 많은 값의 비율 상한), 심각도를 정합니다. 필수값 · 중복데이터 · 더미 값 · 데이터 연속성은 통과 임계값(%)도 정합니다.
  여러 컬럼 키 중복은 테이블마다 키가 달라 지표로 정의하지 않고 데이터셋 품질 탭에서 규칙으로 만듭니다.
  * 날짜 · 여부 · 코드 · 금액 · 수량 · 율은 *기준 방식* 에서 *정규식 패턴* 을 고르면 그 진단 기준의 원래 기준(날짜 형식 · 허용 값 · 범위) 대신
    정규식으로 검증합니다 — 예: 코드가 영문 대문자 3자리(`^[A-Z]{3}$`), 연도가 19·20으로 시작(`^(19|20)\d{2}$`). 리포트에서는 고른 진단 기준으로 집계됩니다.
  * 어느 진단 기준에도 들지 않는 문자열(이메일 · 차량번호 · 사번 등)은 진단 기준 *문자열 형식*(기타)으로 만듭니다.
  * 정규식은 *부분 일치* 입니다. 값 전체가 맞아야 하면 `^` 와 `$` 를 붙입니다.
  * 정규식으로 안 되는 검증(사업자등록번호의 검증 숫자 계산 등)은 *기준 방식* 에서 *Trino 함수 (UDF)* 를 고릅니다. Trino 에 미리
    등록해 둔 함수의 이름만 적습니다 — `카탈로그.스키마.함수` 형태로, 괄호나 인자는 적지 않습니다(예: `memory.default.is_valid_brno`).
    함수는 컬럼 값을 인자 하나로 받아 `boolean` 을 돌려줘야 하고, `true` 가 아니면(`NULL` 반환 포함) 오류로 셉니다. 값이 `NULL` 인
    행은 진단하지 않습니다. 함수의 인자 타입은 컬럼 타입과 맞아야 합니다. 정규식을 쓸 수 있는 진단 기준(유효성 일곱 진단 기준과 문자열 형식)에서
    쓸 수 있습니다. 함수가 등록돼 있지 않으면 진단할 때 그 규칙이 `Function '…' not registered` 오류로 실패합니다.
+
함수는 Trino 에서 다음처럼 등록합니다(함수 저장을 지원하는 카탈로그가 필요합니다).
+
[source,sql]
----
CREATE FUNCTION memory.default.is_zip5(v varchar)
RETURNS boolean
RETURN (regexp_like(v, '^\d{5}$'));
----
  * 진단 기준 선택 상자의 항목에 마우스를 올리면 그 진단 기준이 무엇을 보는지 설명이 나옵니다.
. 이미 있는 지표와 비슷한 것을 만들 때는 목록의 *복사* 를 누릅니다. 원본의 진단 기준 · 기준 · 심각도 · 설명이 채워진 대화상자가 열리고
  이름은 *○○ 복사* 로 들어갑니다. 고친 뒤 저장해야 새 지표가 생기며, 원본에 할당된 컬럼은 복사하지 않습니다.
. 대화상자 아래의 *진단 쿼리 (Trino)* 에 그 기준으로 실행할 쿼리와 통과 판정 방법이 바로 나옵니다. 기준값을 바꾸면 쿼리도 바뀝니다.
  진단이 실제로 쓰는 것과 같은 쿼리이며, 여기서는 만들어 보여 주기만 하고 실행하지는 않습니다.
. 목록의 *할당* 을 눌러 컬럼에 할당합니다.
  * 검색어를 비우면 *추천 컬럼* 이 나옵니다 — 컬럼 이름의 끝 단어(`_yn` · `_cd` · `_amt` · `_cnt` · `_rt` · `_ymd` · `_dt` · `_telno` …)와
    제약(NOT NULL · PK · UNIQUE)으로 보아 그 지표가 맞을 법한 컬럼입니다. 글자 깨짐 · 공백처럼 이름으로 알 수 없는 지표는 추천이 없습니다.
  * 데이터셋이나 컬럼 이름으로 찾으면 추천이 아닌 컬럼도 고를 수 있습니다. 한 번에 300개까지 보입니다.
  * 이름이 같은 데이터셋은 *데이터 소스* 열로 구분합니다.
  * 고른 컬럼마다 그 지표를 가리키는 규칙이 생깁니다. 같은 기준으로 직접 만들어 둔 규칙이 이미 있으면 새로 만들지 않고 그 규칙을 지표에
    연결합니다(진단 결과 이력이 이어집니다).
  * *할당된 컬럼* 의 *쿼리* 를 누르면 그 컬럼의 실제 테이블 이름과 컬럼 타입으로 만든 쿼리가 나옵니다. *해제* 는 그 컬럼의 규칙과 진단 결과를 지웁니다.

지표와 규칙의 관계는 이렇습니다.

* 지표의 유형 · 기준값 · 심각도 · 진단 기준을 바꾸면 할당된 모든 컬럼의 규칙이 *바로* 바뀝니다. 다음 진단부터 새 기준으로 판정합니다.
* 임계값은 지표와 같던 규칙만 따라 바뀝니다. 컬럼마다 따로 준 임계값(예: 한 컬럼만 95%)은 남습니다. 규칙 이름도 지표 이름 그대로인 것만 따라 바뀝니다.
* 지표를 할당한 규칙은 데이터셋의 품질 탭에서 유형 · 기준값 · 심각도를 바꿀 수 없습니다(이름 · 컬럼 · 임계값 · 활성 여부는 됩니다).
  그 컬럼만 다른 기준을 쓰려면 규칙 편집 대화상자의 *연결 끊기* 로 지표에서 떼어 낸 뒤 고칩니다.
* 지표를 삭제해도 할당된 규칙은 지워지지 않고, 각 데이터셋에서 직접 정한 규칙으로 남습니다.
* 그 지표를 진단 범위로 고른(*매핑한 품질 지표만*) 품질 진단 작업이 있으면 삭제 확인 창에 작업 이름이 나옵니다. 삭제 뒤 그 작업들은
  이 지표의 규칙을 진단하지 않습니다(직접 정한 규칙이 되어 *전부* 범위의 작업만 진단). 이 지표 하나만 고른 작업은 *남는 지표 없음* 으로
  표시되며, 진단할 규칙이 없어지므로 작업의 진단 범위를 다시 정하세요. 작업 목록의 품질 지표 열에는 지운 지표가 _삭제된 지표 #N_ 으로
  남고, 그 아래에 _지운 지표 N개는 더 이상 진단하지 않습니다_ 가 나옵니다.

컬럼 간 비교 · 논리관계 · 계산식 · 참조관계 · 행 수처럼 테이블마다 내용이 다른 기준은 지표로 미리 정할 수 없습니다. 데이터셋의 품질 탭에서
규칙으로 직접 만듭니다.

[[help-quality-jobs]]
=== 품질 진단 작업

*품질 진단 작업* 탭에서는 *무엇을(데이터셋), 어떤 품질로(컬럼별 품질 지표), 언제(주기)* 진단할지를 등록해 두고 주기마다 자동으로 진단합니다.
등록 · 수정 · 삭제 · 실행에는 *데이터 품질 관리* (`quality.manage`) 권한이 필요하고, 주기를 두려면 *진단 주기 설정* (`quality.schedule`) 도 필요합니다.

*품질 진단 작업 등록* 을 누르고 다음을 정합니다.

* *진단 대상 데이터셋* — 데이터셋 *하나* 를 고릅니다. 데이터 소스를 고르면 그 데이터셋 목록이 나와 눌러서 고르고(이름을 적어 좁힐 수 있음),
  데이터 소스를 고르지 않고 이름을 2글자 이상 적어 전체에서 찾을 수도 있습니다. 작업 하나가 데이터셋 하나를 진단하며, 여러 테이블을
  진단하려면 테이블마다 작업을 만듭니다. 고르면 Trino 가 그 테이블을 부르는 이름이 옆에 나오고, Trino 로 진단할 수 없는
  데이터셋이면 이유가 나옵니다.
* *컬럼별 품질 지표* — 고른 데이터셋의 컬럼이 표로 나옵니다(컬럼 · 타입 · 품질 지표). 컬럼마다 선택 상자에서 *품질 지표* 탭에
  등록한 지표를 골라 매핑합니다. 한 컬럼에 지표를 여러 개 매핑할 수 있고(예: 필수값 + 우편번호), 매핑한 지표 옆의 × 로 뺍니다.
  *진단 범위* 가 *매핑한 품질 지표만* 이면 하나 이상 매핑해야 저장할 수 있습니다.
+
매핑은 그 데이터셋의 지표 할당과 같은 것입니다. 품질 지표 탭이나 데이터셋 품질 탭에서 이미 할당한 지표가 처음부터 표에 보이고,
여기서 더한 매핑은 저장할 때 할당되어 그 컬럼의 규칙이 생깁니다. 뺀 매핑은 저장할 때 할당이 해제되며 *그 규칙의 지난 진단 결과도
함께 지워집니다* — 표 아래에 몇 개가 해제되는지 미리 나옵니다. 지표 없이 품질 탭에서 직접 만든 규칙은 진단 범위가 *전부* 일 때만 이 작업이 진단합니다.
+
*매핑한 품질 지표만* 진단하는 작업의 지표 목록은 저장할 때 정해집니다. 저장한 뒤 다른 화면에서 이 데이터셋에 더 할당한 지표는 작업을
열면 표에 점선 테두리와 *미포함* 으로 보이고, 표 아래에 _이 작업에는 없는 지표 N개 … 저장하면 이 작업에 포함됩니다_ 가 나옵니다 — 저장하기
전까지 작업은 그 지표를 진단하지 않습니다. 넣지 않으려면 그 매핑을 빼고 저장합니다(할당도 해제됨). 반대로 작업이 진단하던 지표가 지금
매핑에 없으면(다른 화면에서 해제했거나 지표를 지움) 저장할 때 작업에서 빠진다고 알려 줍니다.
+
지표의 *진단 기준* 은 다음과 같습니다. 리포트의 진단 기준별 집계도 이 진단 기준을 씁니다.
+
[cols="1,3,3",options="header"]
|===
| 영역 | 진단 기준 | 해당 규칙 유형
| 완결성 (4) | 글자 깨짐 / 공백·특수문자 / 필수값 / 중복데이터 | 글자 깨짐 / 공백·특수문자 / NULL 없음 / 유일성
| 유효성 (7) | 날짜 / 번호 / 여부 · 코드 / 금액 · 수량 · 율 | 날짜 형식 / 정규식 / 허용 값 / 최솟값 · 최댓값 — 일곱 진단 기준 모두 정규식도 됨
| 정합성 (5) | 시간순서 · 선후관계 / 논리관계 / 계산식 / 참조관계 | 컬럼 간 비교 / 논리관계 / 계산식 / 참조관계
| 기타 | 문자열 형식 / 건수 / 더미 값 / 데이터 연속성 / 값 분포 다양성 / 여러 컬럼 키 중복 | 정규식 / 행 수 / 더미 값 / 데이터 연속성 / 값 분포 다양성 / 여러 컬럼 키 고유값
|===
+
완결성 · 유효성 · 정합성의 16개는 「공공데이터 관리지침」 품질진단 기준과 이름이 같습니다. 허용 값 · 최솟값/최댓값 · 컬럼 간 비교는
한 유형이 진단 기준 여럿에 걸치므로, 규칙마다 어느 진단 기준인지 정합니다 — 규칙 추가 대화상자에서 고른 *진단 기준* 이 그대로 저장됩니다. 품질 지표를
할당한 규칙은 지표의 진단 기준을 따릅니다. 진단 기준을 적지 않고 만든 규칙(규칙 추천 · API · 예전 규칙)은 컬럼 이름의 끝 단어로
정합니다 — `_yn` 은 여부, `_cd` 는 코드, `_amt` · `_fee` 는 금액, `_cnt` · `_qty` 는 수량, `_rt` 는 율. 이름으로 알 수 없으면 코드 · 수량 · 시간순서로
봅니다. 규칙 목록에는 진단 기준, 기준 방식 순으로 보입니다.
+
정규식 규칙은 어느 진단 기준의 값이든 모양을 볼 수 있어, 유효성의 일곱 진단 기준과 *문자열 형식*(진단 기준 16개에 들지 않는 일반 형식 검사)
가운데 고릅니다. 진단 기준을 적지 않은 정규식 규칙은 컬럼 이름으로 추정하지 않고 번호로 셉니다.
+
기준을 바꾸려면 *품질 지표* 탭에서 지표를 고칩니다.
* *진단 범위* — *매핑한 품질 지표만*(새 작업의 기본값)은 매핑한 지표의 규칙만, *데이터셋의 활성 규칙 전부* 는 지표 없이 직접 만든
  규칙과 나중에 더한 규칙까지 모두 진단합니다. 데이터셋 품질 탭의 주기에서 옮겨 온 작업은 *전부* 로 열립니다. *전부* 였던 작업을
  *매핑한 품질 지표만* 으로 바꾸면 줄어드는 범위(빠지는 직접 만든 규칙 수)가 빨간 글로 나옵니다.
* *주기* — 매일(시각) / 매주(요일 · 시각) / 매월(날짜 · 시각, 그 달에 없는 날짜는 말일) / N시간마다 / 수동 실행만. 시각은 Asia/Seoul 기준입니다.
  *주기 실행 사용* 을 끄면 정의는 남기고 자동 실행만 멈춥니다.
* *진단과 함께 프로파일도 수집* — 켜면 회차마다 대상 데이터셋의 프로파일(컬럼 통계)도 대기열에 넣습니다. 규칙이 없는 데이터셋도
  프로파일은 수집합니다. 프로파일이 실패하면 진단이 모두 성공해도 회차가 *일부 실패* 가 되고 사유에 _프로파일 실패 N개_ 가 나옵니다.
  예전 데이터셋 품질 탭의 주기에서 옮긴 작업은 이 옵션이 켜져 있습니다.

목록에는 작업마다 대상, 품질 지표, 주기, 다음 실행 시각, 마지막 실행 결과(상태 · 성공/실패/중지한 데이터셋 수 · 오류율)가 나옵니다.
중지한 데이터셋 진단은 실패와 따로 셉니다.

* *지금 실행* 은 주기와 무관하게 한 번 돌립니다. 다음 실행 시각은 바뀌지 않습니다. 그 데이터셋을 다른 진단(품질 탭의 정밀 진단 등)이
  쓰는 중이면 실행하지 않고 그렇다고 알립니다 — 예약된 차례는 그 진단이 끝날 때까지 미뤘다가 실행합니다.
* 작업을 수정해도 주기를 바꾸지 않았으면 다음 실행 시각은 그대로입니다. *N시간마다* 는 예정 시각을 기준으로 세므로 간격이 밀리지 않습니다.
* 대상 데이터셋이 지워진 작업은 한 번 *실패* 를 남기고 *사용 안 함* 으로 바뀝니다.
* 실행 중에는 *중지* 가 나옵니다 — 아직 끝나지 않은 데이터셋 진단을 모두 멈춥니다.
* 이전 실행이 끝나지 않았는데 다음 차례가 오면 그 차례는 실행하지 않고 *건너뜀* 으로 남깁니다.
* 대상 가운데 진단 경로가 없거나(Trino 연결도 원천 직접 진단도 안 되는 원본, 접속 설정이 없는 데이터 소스) 이미 진단 중인 데이터셋은 시작하지 못하고, 마지막 실행에 _실행하지 못한 데이터셋 N개_ 로 나옵니다.
  이 경우 나머지가 모두 성공해도 상태는 *일부 실패* 입니다.
* 작업을 삭제하면 그 작업 이력도 지워집니다. 이미 진단한 데이터셋의 실행 기록과 규칙 결과는 남습니다.
* 각 데이터셋 진단의 진행은 *실행 현황* 탭에서, 결과는 *작업 이력* 탭에서 봅니다. 작업 행의 시계 아이콘을 누르면 그 작업의 이력이 열립니다.

NOTE: 예전 데이터셋 품질 탭의 *주기*(시간별 · 일별 · 주별)는 없어졌습니다 — 설정돼 있던 주기는 서버가 기동할 때 그 데이터셋 하나를 대상으로 하는 품질 진단 작업(프로파일 수집 켜짐)으로 옮겼습니다.

=== 작업 이력

*작업 이력* 탭은 품질 진단 작업이 한 번 돌 때마다 한 줄씩 쌓입니다. 위의 선택 상자로 작업 하나의 이력만 볼 수 있습니다.

* 열은 *실행 현황* 과 같습니다 — 품질 진단 작업(아래에 데이터셋 · Trino 테이블 · 매핑한 지표), 시작한 방식(예약 또는 실행한 사람)과 시각,
  진행, 경과 시간, 규칙(평가한 수/진단 대상 규칙 수), 진단 · 오류 건수, 오류율(오류 건수 합 ÷ 진단 건수 합), 품질 점수.
  진단 대상 규칙은 그 실행이 고른 범위(품질 지표 · 진단 기준) 안의 활성 규칙입니다 — 작업이 고르지 않은 지표의 규칙이나 지표 없이
  직접 만든 규칙은 세지 않으므로 작업 이력 · 실행 현황 · 리포트 · 데이터셋 품질 탭의 규칙 수가 같습니다. 평가한 수가 더 적으면
  나머지는 경로가 평가하지 못했거나 쿼리가 실패한 규칙입니다.
* *진행* 은 실행 중이면 쿼리 진행 막대, 끝났으면 상태입니다 — *완료* / *일부 실패* / *실패* / *중지됨* / *건너뜀*(이전 실행이 끝나지 않아
  그 차례를 실행하지 않음). 실패 사유가 있으면 상태 아래에 나옵니다.
* 줄을 누르면 그 실행의 상세(개요 · 규칙별 결과 · Trino 쿼리)가 열립니다. 데이터셋 이름을 누르면 그 데이터셋의 품질 탭으로 갑니다.
* 예전 방식으로 여러 데이터셋을 진단한 실행이나 진단을 시작하지 못한 실행은 줄을 누르면 *데이터셋별 결과* 와 시작하지 못한 사유가 펼쳐지고,
  데이터셋을 누르면 그 진단의 상세가 열립니다.
* 실행 중인 작업은 *중지* 할 수 있습니다(*데이터 품질 관리* 권한 필요).
* 작업 실행의 상태 · 집계는 아래 데이터셋 진단이 모두 끝난 뒤 최대 1분 안에(또는 이 화면을 열 때) 마감됩니다.

* 프로파일도 수집하는 작업은 진행 칸에 _프로파일 성공 n/m_ 이 함께 나오고, 펼친 데이터셋별 결과에 프로파일 실행이 *프로파일* 표시와 함께 나옵니다.

* 끝난 줄의 *리포트* 를 누르면 그 작업 실행의 리포트가 열립니다.

=== 리포트

*리포트* 탭은 품질 진단 작업과 작업 실행을 골라 그 결과를 요약해 봅니다. 처음 열면 가장 최근에 실행한 작업의 마지막으로 끝난 실행이 나옵니다.

* 머리글 — 작업 이름과 상태, 시작 시각 · 걸린 시간 · 시작 방식 · 고른 품질 지표. 데이터셋 하나를 진단한 실행이면 그 아래에 데이터셋 이름 ·
  원본 · Trino 테이블이 나오고, *실행 상세(쿼리 보기)* 로 그 진단의 쿼리를 엽니다.
* 핵심 숫자 — *품질 점수*(그 실행에서 평가한 규칙 가운데 통과한 비율, 100점 만점 — 실행 현황 · 작업 이력과 같은 값), *오류율*(오류 건수 ÷ 진단 건수), *오류 건수*(아래에 진단 건수),
  *실패한 규칙*(그 실행에서 평가한 규칙 가운데). 여러 데이터셋을 진단한 실행이면 *진단한 데이터셋*(성공 / 진단한 수)도 나옵니다.
  숫자마다 *직전 대비* 증감이 `▲ 0.12%p (나빠짐)` 처럼 붙습니다 — 같은 작업의 바로 앞 회차(건너뛴 차례 · 실행 중 제외)와 견준 값이고,
  그 회차는 숫자 아래 링크로 엽니다. 첫 회차에는 증감이 없습니다.
* *영역별* · *진단 기준별* — 완결성 · 유효성 · 정합성과 그 아래 진단 기준마다 규칙 수, 실패한 규칙 수, 진단 · 오류 건수, 오류율. 막대는 표에서 가장 높은
  오류율을 기준으로 한 상대 길이입니다. 표 위의 *AI-Ready 품질 지표* 를 누르면 같은 결과를 <<_ai_ready_품질_지표,AI-Ready 지표>>(완전성 · 일관성 · 정확성 ·
  적시성 · 유효성 · 유일성)와 세부 지표로 묶어 보여 줍니다(*관리지침 진단 영역* 으로 되돌아감). 건수 기준은 AI-Ready 묶음에서 빠집니다.
* *규칙별 결과* — 그 실행에서 평가한 규칙을 실패한 것부터 보여 줍니다: 컬럼, 규칙(유형), 진단 기준, 할당된 품질 지표, 결과, 진단 · 오류 건수,
  오류율, 상세. 30건을 넘으면 *나머지 보기* 로 펼칩니다.
* *회차별 추이* — 같은 품질 진단 작업의 최근 30회 오류율입니다. 오른쪽 선택 상자로 전체 또는 진단 기준 하나를 고릅니다. 큰 점이 지금 보고 있는 실행입니다.
  건너뛴 차례와 실행 중인 것은 빠집니다.
* *데이터셋별* — 여러 데이터셋을 진단한 실행에만 나옵니다. 오류율이 높은 순서이고, 데이터셋을 누르면 그 진단의 실행 상세가 열립니다.
* *PDF 내려받기* — 인쇄·공유용 한 문서(A4 가로)입니다. 핵심 숫자(품질 점수 · 오류율 · 진단/오류 건수 · 실패한 규칙 · 진단한 데이터셋), 실행 정보, 영역별 · 진단 기준별 · AI-Ready 품질 지표별 · 데이터셋별 표, 시작하지 못한 데이터셋, 규칙별 결과가 차례로 나옵니다. 규칙별 표는 실패한 규칙을 먼저 싣고, 규칙이 1,000건을 넘으면 1,000건만 싣습니다 — 전체는 엑셀로 받으세요. 한글 글꼴(Noto Sans KR)을 문서에 넣으므로 어느 PC 에서 열어도 같게 보이지만, 이름·상세에 한자나 이모지가 있으면 그 글자는 빈 네모로 나옵니다.
* *엑셀 내려받기* — 요약 · 진단 기준별 · AI-Ready 지표별 · 데이터셋별 · 규칙별 다섯 시트입니다. AI-Ready 지표별 시트는 지표 합계 행 뒤에 진단 기준 행이 옵니다. 규칙별 시트에는 규칙에 할당된 품질 지표 이름도 나옵니다. 시작하지 못한 데이터셋과 사유는 요약 시트에 있습니다.
* PDF · 엑셀의 시각은 화면과 같은 시간대(내려받는 브라우저의 시간대, 알 수 없으면 Asia/Seoul)이고 머리글에 시간대 이름(예: KST)을 밝힙니다.
  심각도(치명 · 경고 · 정보)와 규칙 유형(NULL 없음 · 고유값 …)도 화면과 같은 이름으로, 데이터셋별 표의 대상은 진단 경로와 관계없이 *진단 테이블* 열로 적습니다.

실행의 *품질 점수* 는 그 실행에서 평가한 규칙만 셉니다 — 품질 지표를 골라 규칙 3개만 진단해 2개가 통과하면 66.7 입니다. 데이터셋 화면의
품질 점수는 다릅니다: 데이터셋의 활성 규칙 전체가 기준이고, 이번에 진단하지 않은 규칙은 직전 결과를 이어받습니다. 점수는 규칙 수 기준이라
건수 기준인 오류율과 같이 움직이지 않습니다. 데이터셋 품질 탭의 상태 카드에는 작업이 넣은 실행이면 *작업 실행 · <작업 이름>* 과 *실행 점수* 가
나오고, 이어받은 결과가 있으면 두 점수의 기준이 다르다는 안내가 붙습니다. 결과 표에서 이어받은 규칙에는 *이전 결과* 가 붙습니다.

오류율은 규칙마다 구한 진단 건수와 오류 건수를 각각 더해 나눈 값입니다. 규칙이 잘못돼 쿼리가 실패한 규칙은 건수가 없어 분자 · 분모에서
빠지고 *실패한 규칙* 에만 들어갑니다. Trino 장애로 진단하지 못한 규칙은 그 회차의 결과가 없으므로 어디에도 들어가지 않습니다.

지난 회차의 리포트는 진단 당시의 진단 기준 · 품질 지표 · 규칙 이름으로 보여 줍니다 — 그 뒤에 지표의 기준을 바꿔도 달라지지 않습니다. 진단 뒤에
지운 규칙(할당 해제 포함)은 결과도 지워지므로 표에서 빠지고, 몇 개가 빠졌는지 표 아래에 나옵니다.

목록이나 리포트를 불러오지 못하면 그 사유와 *다시 시도* 단추가 나옵니다. 주소로 연 작업이 지워졌거나 작업 실행이 없으면 그렇다고 알립니다.

== 원천 데이터 시간대

`FRESHNESS` 에서 시간대 정보가 없는 시각 값(MySQL `DATETIME`, PostgreSQL `timestamp` 등)을 어느 시간대로 해석할지 정하는 설정입니다.
시간대가 있는 값(PostgreSQL `timestamptz` 등)은 자기 시간대를 그대로 씁니다. 정밀 진단은 실행을 만들 때의 값을 실행에 담아 품질 워커에 넘기므로
Trino 경로와 원천 직접 경로가 같은 기준으로 판정합니다.

카탈로그 설정 `quality_source_timezone` (기본 `Asia/Seoul`)으로 정합니다. 화면 메뉴는 없고 API 로 조회 · 변경합니다.
조회는 `GET /api/v1/quality/settings`, 변경은 관리자만 `PUT /api/v1/quality/settings` 로 하며 변경 내역은 감사 로그에 남습니다.

[TIP]
.고급 사용자 — 시간대를 API 로 바꾸기
====
[source,bash]
----
curl -X PUT <카탈로그 주소>/api/v1/quality/settings \
  -H "Authorization: Bearer <관리자 토큰>" -H "Content-Type: application/json" \
  -d '{"source_timezone": "UTC"}'
----
====

값은 IANA 이름(`Asia/Seoul`, `UTC`) 또는 `+09:00` 형식입니다. 알 수 없는 시간대는 서버가 거부(422)합니다.

[NOTE]
.품질 배치는 없앴습니다
====
원본 DB 를 직접 읽어 결과를 반입하던 명령줄 스크립트 *품질 배치* (`quality/`, pandas · PySpark)와 반입 API 는 없앴습니다.
같은 일은 품질 워커가 합니다 — Trino 커넥터가 없는 원본은 *원천 직접* 경로로, 커스텀 Python 플러그인도 워커의 `custom_checks/` 에서 돌립니다.
외부 스케줄러에 등록해 두던 배치는 <<help-quality-jobs,품질 진단 작업>> 으로 옮기세요.
====

== 자주 묻는 질문

[qanda]
규칙에 *정밀 진단 제외* 가 붙고 결과가 *미평가* 로 나옵니다.::
  그 데이터셋의 진단 경로가 평가하지 않는 유형입니다 — 원천 직접 경로의 커스텀 SQL · Trino 함수, 원본을 직접 읽을 수 없는(지원하지 않는 유형 · 접속 설정 없음) Trino 경로의 커스텀 Python.
  Trino 경로를 쓰려면 데이터 소스에 *카탈로그 연결* 을 하고, 아니면 같은 검사를 다른 유형(예: 커스텀 Python)으로 만드세요.

원본 데이터를 고쳤는데 점수가 그대로입니다.::
  점수는 마지막 정밀 진단 결과입니다. *정밀 진단* 을 다시 실행하거나 다음 품질 진단 작업 회차를 기다리세요.

최신성 규칙이 *최신성 검사는 적재 · 수정 시각 컬럼을 지정해야 합니다* 로 실패합니다.::
  예전에 컬럼 없이 만든 규칙입니다. 규칙을 열어 적재 · 수정 시각 컬럼을 고르세요.

*프로파일 실행* · *정밀 진단* · *규칙 추가* 버튼이 보이지 않습니다.::
  해당 기능 권한이 제한된 역할입니다. 관리자에게 요청하세요.

== 사용 시나리오

데이터 신뢰성 확인 (분석가)::
품질 탭 → 데이터 프로파일 구역의 *프로파일 실행* → NULL · 고유 비율 · 값 범위 확인 → 이상치를 발견하면 원천 담당자에게 확인합니다.

핵심 테이블 SLO 설정 (DBA)::
주문 · 결제 같은 핵심 테이블에서 *규칙 추천* 으로 기본 규칙을 만들고, PK `UNIQUE` 를 *치명* 으로, 금액 `MIN_VALUE` 0,
`ROW_COUNT`, 수정 시각 컬럼을 지정한 `FRESHNESS` 24 를 추가 → 품질 진단 작업을 *매일* 로 등록 → 점수 추세로 모니터링합니다.

코드값 · 형식 진단 (데이터 엔지니어)::
상태 코드에 `ACCEPTED_VALUES`, 이메일에 `REGEX`, 참조 무결성에 `REFERENTIAL` 을 등록 → <<help-quality-jobs,품질 진단 작업>> 을 매일 야간으로 등록 →
아침에 품질 탭에서 실패 규칙의 *위반 샘플* 을 확인합니다.

전사 품질 거버넌스::
데이터셋 품질 상태(GOOD · WARN · BAD)로 낮은 데이터셋을 먼저 정제하고, xref:governance/alerts.adoc[알림] 규칙과 결합해
품질 실패를 자동으로 통보받습니다. 파생 데이터셋은 *업스트림 품질 경고* 로 원천 문제를 함께 추적합니다.
