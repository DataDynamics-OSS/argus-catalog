= 플러그인 사용·운영

플러그인을 배포한 뒤 사용자에게 어떻게 보이는지, 관리자가 무엇을 설정하는지, 문제가
생겼을 때 어디를 보면 되는지 정리합니다.

== 사용자에게 보이는 모습

플러그인 화면은 코어 화면과 똑같이 사이드바 메뉴로 들어갑니다.

* 플러그인이 *새 메뉴 그룹* 을 정의하면, 그 그룹은 사이드바의 *관리* 그룹 바로 위에 추가됩니다.
* 플러그인 메뉴 그룹 `id` 가 기존 그룹과 같으면, 그 그룹 끝에 메뉴 아이템이 덧붙습니다.
* 화면 주소는 모두 `/dashboard/x/<slug>` 형태입니다(예: `/dashboard/x/acme/billing`).
* 화면은 코어의 헤더·카드·표 컴포넌트를 재사용하므로 코어 화면과 같은 모양으로 보입니다.

== 권한 설정

=== 메뉴 노출 — 권한 관리 화면

켜져 있는 플러그인의 메뉴 아이템은 *관리 → 권한 관리* 화면의 *메뉴 권한* 표에 자동으로
행이 추가됩니다. 코어 메뉴와 같은 방법으로 역할별 노출 여부를 체크합니다.

[cols="1,3"]
|===
| 항목 | 값

| 메뉴 키 | `plugin.<메뉴 아이템 id>` (예: `plugin.acme-billing`)
| 그룹 | 플러그인 메뉴 그룹의 `label` (예: `ACME`). 표에서 *관리* 그룹 바로 앞에 표시
| 기본값 | 다른 메뉴와 마찬가지로 *설정하지 않으면 모든 역할에 노출*
|===

관리자 전용으로만 두려면 개발 단계에서 메뉴 아이템에 `adminOnly: true` 를 지정합니다
(xref:plugin/frontend.adoc[프론트엔드 화면 플러그인] 참고). 이 경우 권한 관리 화면 설정과
관계없이 관리자에게만 보입니다.

=== 화면 접근 차단

권한 관리 화면의 설정과 `adminOnly` 는 사이드바 메뉴뿐 아니라 *화면 접근* 에도 같은
기준으로 적용됩니다. 권한이 없는 사용자가 주소(`/dashboard/x/...`)를 직접 입력하면
화면 대신 *접근 권한 없음* 안내가 표시됩니다. 관리자는 항상 모든 플러그인 화면에 접근할
수 있습니다.

=== 화면 차단과 데이터 보호는 다릅니다

[WARNING]
====
화면 접근 차단은 브라우저에서 이뤄지는 *UI 게이팅* 입니다. API 를 직접 호출하는 것까지
막지는 못하므로, 실제 데이터 보호는 플러그인 백엔드 API 의 인증·권한 의존성이 담당합니다. 민감한 데이터를 다루는 플러그인은
API 에 `require_admin` 이나 `require_feature(...)` 를 걸었는지 확인하세요
(xref:plugin/backend.adoc[백엔드 API 플러그인] 의 *인증* 참고).
====

=== 플러그인을 끈 상태에서 권한을 저장할 때

권한 관리 화면은 저장할 때 *화면에 보이는 메뉴 목록으로 메뉴 권한 전체를 덮어씁니다*.
플러그인을 끈 상태(프론트 레지스트리에서 제외)로 메뉴 권한을 저장하면 그 플러그인 메뉴에
걸어 둔 제한도 함께 지워집니다. 플러그인을 다시 켜면 기본값(모든 역할 노출)으로 돌아오므로,
필요하면 권한을 다시 설정합니다.

== 동작 확인

=== 백엔드

서버 기동 로그에서 플러그인 등록 결과를 확인합니다.

[source,text]
----
플러그인 'acme' 등록 완료 (prefix=/api/v1)
플러그인 1개 로드됨: acme
----

API 는 로그인 토큰을 붙여 호출합니다. 토큰 없이 호출하면 `401` 이 정상입니다.

[source,bash]
----
curl -s -H "Authorization: Bearer <토큰>" localhost:4600/api/v1/acme/billing/summary
----

=== 프론트엔드

* 사이드바에 플러그인 메뉴가 보이는지 확인합니다.
* 메뉴를 눌러 화면이 열리는지, 화면에서 호출하는 API 가 정상 응답하는지 확인합니다.
* *권한 관리* 화면의 메뉴 권한 표에 `plugin.<아이템 id>` 행이 생겼는지 확인합니다.

== 문제 해결

=== 백엔드 로그 메시지

코어 로더(`backend/app/plugins.py`)는 플러그인 하나가 실패해도 서버 기동과 다른 플러그인에
영향을 주지 않고, 원인을 로그로만 남깁니다.

[cols="2,3"]
|===
| 로그 메시지 | 원인과 조치

| `플러그인 '<이름>' 비활성(plugins.enabled 미포함) — 건너뜀`
| `plugins.enabled` 에 이름이 없습니다. 켜려면 목록에 추가하고 재시작합니다.

| `플러그인 '<이름>' 로드 실패 — 건너뜀` (스택 트레이스 동반)
| 패키지 import 중 예외가 났습니다. 스택 트레이스의 import 오류·의존성 누락을 확인합니다.

| `플러그인 '<이름>' 에 router 속성이 없음 — 건너뜀`
| entry point 가 가리키는 객체에 `router` 가 없습니다. `__init__.py` 의 `plugin` 객체를 확인합니다.

| `플러그인 '<이름>' 라우터 등록 실패 — 건너뜀`
| `router` 가 FastAPI `APIRouter` 가 아니거나 `prefix` 형식이 잘못됐습니다.

| `plugins.enabled 에 있으나 설치되지 않은 플러그인: <이름>`
| 설정에 적은 이름의 플러그인이 설치돼 있지 않습니다. 이름 오타나 설치 누락을 확인합니다.

| 플러그인 관련 로그가 전혀 없음
| entry point 가 발견되지 않았습니다. 백엔드와 *같은 Python 환경* 에 설치했는지 확인합니다
  (xref:plugin/configuration.adoc[설정·배포] 의 설치 확인 명령 참고).
|===

=== 증상별 점검

[cols="2,3"]
|===
| 증상 | 점검할 곳

| 사이드바에 메뉴가 없음
| ① `registry.ts` 에 등록 후 다시 빌드했는지 ② 권한 관리 화면에서 내 역할이 막혀 있지 않은지
  ③ `adminOnly: true` 인데 관리자가 아닌지

| 화면에 *접근 권한 없음* 이 표시됨
| 권한 관리 화면에서 내 역할이 해당 `plugin.<아이템 id>` 메뉴에 허용돼 있는지, 메뉴가
  `adminOnly: true` 인지 확인합니다.

| 메뉴를 누르면 404 화면
| 메뉴 `url` 의 `/dashboard/x/` 뒤 경로와 화면 `slug` 가 정확히 같은지

| 메뉴 아이콘이 물음표(?)로 보임
| 메뉴 `icon` 이름이 코어 아이콘에도, 플러그인 `icons` 에도 없습니다. `icons` 에 추가합니다.

| 화면은 열리는데 데이터 호출이 404
| 백엔드 플러그인이 설치·활성화되지 않았습니다. 서버 로그를 확인합니다.

| 화면은 열리는데 데이터 호출이 401/403
| 로그인 토큰이 없거나(401), API 에 건 권한 의존성에 막혔습니다(403).

| 플러그인 API 경로가 코어 API 와 겹침
| 코어 라우터가 먼저 등록되므로 코어가 응답합니다. 플러그인 `prefix`·경로를 바꿉니다.
|===
