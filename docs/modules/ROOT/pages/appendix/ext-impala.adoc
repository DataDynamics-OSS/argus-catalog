= Impala Query Agent

ASM 기반의 *bytecode instrumentation agent* 입니다. Impala Frontend 의
`createExecRequest` 메서드를 계측해서 쿼리 이벤트를 비동기로 수집합니다.

== 요구사항

* Impala 4.0+ (Apache Impala, Java Frontend)
* Impala 3.x (CDP 7.x) 도 호환
* JDK 11+

== 빌드

아래 명령으로 빌드합니다.

[source,bash]
----
mvn clean install
----

빌드가 끝나면 다음 산출물이 만들어집니다.

* `target/impala-query-agent-1.0.0.jar` — ASM + Jackson 포함 (shade plugin)

== 동작 원리

이 에이전트가 impalad JVM 안에서 어떻게 쿼리를 가로채고 전송하는지를 정리하면 다음과 같습니다.

----
Impala Daemon (impalad) JVM
├─ Frontend.createExecRequest(TQueryCtx, ...)
│   └─ ASM Instrumented
│       ├─ onMethodEnter → QueryInterceptor.onQueryStart()
│       ├─ ... original method ...
│       └─ onMethodExit  → QueryInterceptor.onQueryComplete()
│
└─ QuerySender (async thread)
    └─ POST /collector/impala/query → Metadata Sync (4610)
----

ASM Instrumentation 대상은 다음과 같습니다.

* *클래스* — `org.apache.impala.service.Frontend`
* *메서드* — `createExecRequest` (public overload)
  ** Impala 3.x — `createExecRequest(TQueryCtx, StringBuilder)`
  ** Impala 4.0+ — `createExecRequest(PlanCtx)` → `PlanCtx.getQueryContext()` 로 TQueryCtx 추출
* 데이터 접근 — *Reflection* 사용 (Thrift 객체 컴파일 의존성 없음)
* *버전 자동 감지* — `PlanCtx` 클래스 존재 여부로 3.x / 4.x 판별

== 버전 호환성

Impala 버전에 따라 `createExecRequest` 의 시그니처가 다른데, 에이전트는 이를 자동으로 감지해 양쪽 모두를 지원합니다.

[cols="1,3,1,2"]
|===
| Impala 버전 | createExecRequest 시그니처 | 첫 인자 | TQueryCtx 접근

| 3.x (CDP 7.x) | `(TQueryCtx, StringBuilder)` | TQueryCtx | 직접 사용
| 4.0 ~ 4.4+ | `(PlanCtx)` | PlanCtx | `getQueryContext()`
|===

`TQueryCtx.client_request.stmt`, `session.connected_user`, `session.delegated_user`
와 `TExecRequest.query_exec_request.query_plan` 의 내부 구조는 3.x ~ 4.x 전 버전에서 동일하기 때문에 추가 분기 없이 그대로 사용합니다.

== 수집 정보

에이전트가 쿼리 한 건마다 수집하는 필드는 다음과 같습니다.

[cols="2,3"]
|===
| 필드 | 설명

| `timestamp` | 쿼리 시작 시각 (epoch ms)
| `query` | SQL 텍스트 (`TQueryCtx.client_request.stmt`)
| `plan` | 실행 계획 (`TExecRequest.query_exec_request.query_plan`)
| `connectedUser` | 인증된 연결 사용자
| `delegateUser` | 위임 사용자 (proxy)
| `effectiveUser` | 실제 실행 사용자 (delegate 우선, 없으면 connected)
| `platformId` | Argus Catalog 플랫폼 ID (agent 파라미터)
|===

== 전송 페이로드

수집한 정보는 다음과 같은 JSON 형태로 Metadata Sync 에 전송됩니다.

[source,json]
----
{
  "timestamp": 1742536200000,
  "query": "SELECT a.id, b.name FROM db.table_a a JOIN db.table_b b ON a.id = b.id",
  "plan": "01:EXCHANGE [UNPARTITIONED]\n|  ...\n00:SCAN HDFS [db.table_a a]\n   ...",
  "connectedUser": "alice",
  "delegateUser": "bob",
  "effectiveUser": "bob",
  "platformId": "impala-19d0bfe954e3fd2cd"
}
----

== 설정

에이전트는 Impala Daemon 의 JVM 옵션으로 부착합니다.

[source,bash]
----
JAVA_TOOL_OPTIONS="-javaagent:/opt/argus/impala-query-agent-1.0.0.jar=targetUrl=http://<metadata-sync>:4610/collector/impala/query,platformId=impala-19d0bfe954e3fd2cd"
----

에이전트에 넘길 수 있는 파라미터는 다음과 같습니다.

[cols="2,1,2,3"]
|===
| 파라미터 | 필수 | 기본값 | 설명

| `targetUrl` | Yes | - | 수집 엔드포인트 URL
| `platformId` | Yes | - | Argus Catalog 플랫폼 ID
| `enabled` | No | `true` | Agent 활성화
|===

== Cloudera Manager 설정

Cloudera Manager 를 사용한다면 *Cloudera Manager → Impala → Configuration → Impala Daemon Java
Configuration Options for Impala Daemon* (또는 Safety Valve) 에 다음 옵션을 추가합니다.

----
-javaagent:/opt/argus/impala-query-agent-1.0.0.jar=targetUrl=http://<metadata-sync>:4610/collector/impala/query,platformId=impala-19d0bfe954e3fd2cd
----

== 배포 순서

다음 순서대로 진행합니다.

. 빌드한 `impala-query-agent-1.0.0.jar` 를 *모든 Impala Daemon 노드* 에 배포합니다.
. Cloudera Manager 에서 JVM 옵션을 추가한 뒤 Impala 서비스를 재시작합니다.
. Metadata Sync 서버의 `/collector/impala/query` 에서 수신이 되는지 확인합니다.

== 주의사항

확장을 적용하기 전에 다음 사항을 알아 두면 좋습니다.

* 전송은 daemon thread 에서 비동기로 이뤄지므로 Impala 의 쿼리 처리에는 영향을 주지 않습니다.
* ASM 은 maven-shade-plugin 으로 relocate 하여 Impala 내부 라이브러리와 충돌하지 않도록 했습니다.
* Reflection 기반이라 대상 메서드가 없으면 null 을 반환하여 호환성을 유지합니다.
