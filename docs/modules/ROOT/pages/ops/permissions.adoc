= 권한 관리
:toc: macro
:toclevels: 2

**권한 관리** 화면에서는 역할별로 **어떤 메뉴를 볼 수 있는지**(메뉴 권한)와 **메뉴 안의 어떤 기능을 쓸 수 있는지**
(기능 권한)를 정합니다. 사용자에게 역할을 주는 일은 xref:ops/users.adoc[사용자 관리] 에서 합니다.

이 문서는 처음 사용하는 분을 기준으로 화면 순서대로 설명합니다.

toc::[]

== 시작하기 전에

=== 이런 일을 할 수 있습니다

* **메뉴 숨기기** — 역할별로 사이드바 메뉴를 열거나 막습니다.
* **기능 막기** — 메뉴 안의 버튼 · 탭 · 민감 데이터(샘플 데이터, 접속 정보 등)를 역할별로 통제합니다.
* **한꺼번에 바꾸기** — 역할 전체 · 그룹 단위 · 항목 하나씩 체크를 바꿉니다.
* **저장 전에 미리 보기** — 역할별로 보이게 될 메뉴와 기능을 미리 확인합니다.
* **역할 만들기** — 부서 · 직무별 역할을 만들어 표의 열로 씁니다(<<_사용자_정의_역할>>).
* **보기 전용** — 메뉴는 열어 두되 그 메뉴의 편집 기능을 막습니다(<<_메뉴_보기_전용>>).
* **변경 이력 확인** — 누가 언제 권한을 바꿨는지 봅니다.

=== 먼저 알아 둘 용어

[cols="1,3",options="header"]
|===
| 용어 | 뜻

| 메뉴 권한 | 사이드바 메뉴를 볼 수 있는지 정합니다.
| 기능 권한 | 메뉴 안의 버튼 · 탭 · 민감 데이터를 쓸 수 있는지 정합니다.
| 역할 | 관리자(Admin) · 슈퍼유저(Superuser) · 사용자(User). 자세한 설명은 xref:ops/users.adoc#_역할[사용자 관리 → 역할] 을 보세요.
|===

== 기본 규칙 — 먼저 읽어 주세요

* **관리자(Admin)는 항상 모든 권한** 을 가집니다. 표의 Admin 열은 항상 체크된 채 잠겨 있습니다.
* 설정하는 대상은 **슈퍼유저(Superuser)** 와 **사용자(User)** 두 역할, 그리고 직접 만든 <<_사용자_정의_역할,사용자 정의 역할>> 입니다.
* **설정하지 않은 항목은 모든 역할에 허용** 됩니다 (open-by-default). 잠그고 싶은 항목만 체크를 해제하세요.
* 단, 설명에 **"미설정 시 관리자만"** 이라고 적힌 기능은 반대로 **명시 허용형** 입니다. 허용할 역할을 직접 체크해야
  그 역할이 쓸 수 있습니다.
* 관리 메뉴(사용자 관리 · 메타데이터 수집 · 데이터 품질 · 설정 · 감사 로그 · 권한 관리)는 **관리자 전용(고정)** 이라 메뉴 권한 표로 다른 역할에 열 수 없습니다.
  대신 연결된 기능 권한을 허용받은 역할에 열립니다(표에는 *관리자 + ○○ 권한* 으로 표시) — *메타데이터 수집* 은 `datasources.sync`,
  *데이터 품질* 은 `quality.manage`, *사용자 관리* 는 `users.manage`, *설정* 은 `settings.*` 중 하나, *감사 로그* 는 `audit.view`.
  *권한 관리* 는 늘 관리자만 씁니다.
  자세한 내용은 <<_관리_기능_위임>> 을 보세요.
* 저장한 내용은 서버 API 검사에는 바로 적용되고, 사용자 화면에는 탭으로 돌아오거나 1분 안에 반영됩니다.

== 메뉴 권한

image::ops-permissions/menu.png[메뉴 권한, 900]

메뉴는 사이드바와 같은 그룹(데이터 카탈로그 · AI 카탈로그 · API 카탈로그 · 거버넌스 · 관리)으로 묶여 있습니다.
메뉴를 막으면 사이드바에서 숨겨지고, 주소를 직접 입력해 들어와도 페이지를 열 수 없습니다.

. 막을 메뉴를 찾아 해당 역할(Superuser / User) 열의 체크를 해제합니다.
. 표 오른쪽 위의 **저장** 을 누릅니다 (<<_저장_취소>> 참고).

각 메뉴 이름 옆의 배지는 막았을 때 어디까지 막히는지 알려 줍니다.

[cols="1,3",options="header"]
|===
| 배지 | 의미

| 서버 API 차단
| 화면뿐 아니라 그 메뉴의 API 를 직접 호출해도 서버가 403 으로 막습니다.
| 편집 서버 차단
| 데이터 표준 · 용어집 · 태그 · 분류 체계 · 오류 신고 처리. 조회 API 는 데이터셋 화면도 함께 써서 열어 두지만, 메뉴를 막은 역할은
  그 메뉴의 편집 기능(`standards.edit` · `glossary.edit` · `tags.manage` · `taxonomies.edit` · `data-reports.handle`)을 서버에서도 쓸 수 없습니다.
  데이터셋 분류 매핑(`taxonomies.map`)은 데이터셋 화면에서도 쓰므로 분류 체계 메뉴와 묶지 않고, 데이터셋 메뉴의 보기 전용에 묶입니다.
| 화면만
| 여러 메뉴가 함께 쓰는 API 라서 화면에서만 막습니다. 데이터 자체를 감춰야 한다면 기능 권한을 함께 쓰세요.
| 관리자 전용(고정)
| 관리 메뉴입니다. 바꿀 수 없습니다.
|===

메뉴를 막았을 때 함께 막히는 API 는 다음과 같습니다.

* *MLflow 모델* — 화면 API 와 MLflow 클라이언트용 API(`/api/2.1/unity-catalog`), 그 메뉴 모델의 파일 다운로드 주소 · 파일 목록 · manifest.
* *OCI 모델 허브* — 화면 API 와 그 메뉴 모델의 파일 다운로드 주소 · 파일 목록 · manifest.
* *알림* — 알림 목록 · 규칙 API 와 머리글의 알림 벨.
* *AI-Ready 점검* — 점검 목록(전체 데이터셋 충족률)과 범위 선택지 API. 데이터셋 상세의 AI-Ready 탭은 그대로 열립니다.
* *데이터셋* — 데이터셋 시맨틱 · 하이브리드 검색 API. 통합 검색은 데이터셋 결과만 빈 목록으로 돌려줍니다.

=== 한꺼번에 바꾸기

체크박스는 세 단계로 한꺼번에 바꿀 수 있습니다.

* **역할 열 머리글** (Superuser / User 옆) — 그 역할의 모든 항목을 허용하거나 해제합니다.
* **그룹 행** (진한 배경의 그룹 이름 줄) — 그 그룹에 속한 항목만 허용하거나 해제합니다.
* **항목 행** — 하나씩 바꿉니다.

일부만 허용된 그룹이나 역할은 체크박스에 `−` 표시가 나타납니다.

== 기능 권한

image::ops-permissions/feature.png[기능 권한, 900]

기능 권한은 메뉴 안의 버튼 · 탭 · 민감 데이터를 역할별로 통제합니다. 어느 메뉴의 기능인지에 따라 그룹으로
묶여 있고, 그룹 이름을 누르면 접히거나 펼쳐집니다. **전체 펼치기 / 접기** 로 한꺼번에 바꿀 수 있습니다.

권한이 없는 기능은 화면에서 버튼이나 메뉴가 숨겨지거나 비활성화되고, 서버도 같은 기준으로 403 을 돌려줍니다
(**화면만** 배지가 붙은 기능은 화면에서만 숨깁니다).

TIP: 권한을 통과하더라도 데이터셋 · 모델 · 배포처럼 **소유자가 있는 자산** 은 소유자(또는 관리자)만 수정할 수 있습니다.
데이터셋의 소유자는 생성자와 메타데이터 탭 *소유자* 목록의 사용자입니다 — 목록의 사용자도 메타데이터 · 스키마 · 품질 · AI 생성 · AI-Ready
같은 일반 편집을 하지만, 데이터셋 삭제와 *소유자* 추가 · 삭제는 생성자와 관리자만 합니다(권한 상승 방지).
기능 권한은 "이 역할이 이 기능을 쓸 수 있는가"를, 소유권은 "이 자산을 고칠 수 있는가"를 정합니다.
수정 · 삭제 · 내려받기 권한은 둘 다 통과해야 합니다 — 예를 들어 `datasets.delete` 를 해제한 역할은 자기 데이터셋도 지울 수 없습니다.

NOTE: 메타데이터 동기화(`datasources.sync`) 권한을 받은 역할은 데이터셋 정보 수정 · 스키마 편집을 해제해도 수집이 계속됩니다.
수집 어댑터가 같은 API 로 원본 메타데이터를 반영하기 때문입니다.

== 저장 · 취소

메뉴 권한 · 메뉴 보기 전용 · 기능 권한은 표마다 따로 저장합니다.

. 체크를 바꾸면 표 오른쪽 위에 **저장 안 된 변경 N건** 이 나타나고 **저장** 이 켜집니다.
. **저장** 을 누르면 적용됩니다. **변경 취소** 를 누르면 마지막으로 저장한 상태로 돌아갑니다.

저장하지 않은 채 브라우저 탭을 닫거나 새로고침하면 확인을 묻습니다.

여러 관리자가 같은 표를 동시에 고치면, 먼저 저장한 내용을 덮어쓰지 않도록 나중 저장은 거부되고
"다른 관리자가 먼저 저장했습니다" 안내와 함께 최신 상태를 다시 불러옵니다. 바꾸려던 체크를 다시 적용해 저장하세요.

== 변경 이력

오른쪽 위의 **변경 이력** 은 권한 매트릭스 · 보기 전용 · 역할을 누가 언제 어떻게 바꿨는지 보여 줍니다. 사용 방법은
xref:ops/users.adoc#_사용자_변경_이력[사용자 관리 → 변경 이력] 과 같습니다.

권한이 없어 거부된 요청(403)도 *권한 거부* 로 남습니다 — 누가 어떤 권한으로 어느 주소에서 거부됐는지.
권한 변경 · 거부 기록은 관리자가 아니어도 `audit.view` 를 받은 역할이 xref:ops/audit.adoc[감사 로그] 화면에서 *권한 관리* 범주로 걸러 봅니다.
남는 거부는 다음과 같습니다.

* 메뉴 · 기능 권한(보기 전용 메뉴의 쓰기 포함), 데이터셋 직접 등록, 사용자 관리를 위임받지 않은 사람의 남의 프로필 수정
* 관리자 전용 기능(권한 관리 · 역할 변경, 관리자만 지정할 수 있는 상태 등)을 관리자가 아닌 사람이 부른 경우
* 소유자 확인 — 남의 데이터셋 · API · 댓글 · 변경 요청 · 모델 · AI 에이전트 · MCP 서버 등을 소유자도 관리자도 아닌 사람이 고치거나 지운 경우
* 위임 범위 — 사용자 관리 · API 키 관리를 위임받은 사람이 관리자 계정이나 자기가 줄 수 없는 역할의 계정 · 키를 다루려 한 경우(권한 상승 시도)

이 밖에 업무 흐름이나 대상에 따라 거부하는 요청(예: 결재 차례가 아닌 변경 요청 승인, 알림 상태 변경, 허용 범위 밖의
파일 경로, 비활성 계정 로그인)은 권한 거부로 남지 않고 서버 로그에만 남습니다.

같은 사람이 같은 권한으로 거부되면 1분에 한 번만 남겨 기록이 넘치지 않게 합니다(관리자 전용 · 소유자 · 위임 범위는 주소마다).

== 관리 기능 위임

관리자 한 사람이 모든 운영 업무를 맡지 않도록, 관리 메뉴의 일부를 역할에 나눠 줄 수 있습니다. 위 기능 권한 표의
*관리 (관리 기능 위임)* 그룹이 그 대상이며 모두 명시 허용형입니다(체크하지 않으면 지금처럼 관리자만).

* *사용자 관리* (`users.manage`) 를 받으면 사이드바에 *사용자 관리* 가 열립니다.
* *설정* 은 `settings.*` 중 하나라도 받으면 열리고, 받은 항목의 탭만 보입니다. 예를 들어 `settings.mail` 만 받은 역할은
  *이메일* 탭만 봅니다.
* *감사 로그* (`audit.view`) 를 받으면 사이드바에 xref:ops/audit.adoc[감사 로그] 가 열려 모든 범주(권한 변경 · 거부 포함)를 봅니다.
  *변경 이력* 단추(사용자 관리 · 설정 · 권한 관리 화면)도 `audit.view` 가 있을 때만 보입니다.

다음은 위임할 수 없고 늘 관리자만 합니다.

* 권한 관리 화면, 사용자의 역할 변경
* 설정 › 인증(Keycloak) · CORS · 데이터셋 등록 · 쿼리 분석 · 변경관리

IMPORTANT: 위임받은 사람이 자기보다 넓은 권한을 얻는 길을 막기 위해, 위임받은 사람은 **기본 사용자 역할(`argus-user`)과 자기 역할**
의 계정만 만들고 수정 · 비밀번호 재설정 · 활성 · 비활성 · 잠금 해제 · 삭제할 수 있습니다. 관리자 · 슈퍼유저 · 다른 사용자 정의 역할의
계정은 다룰 수 없고(본인 계정은 예외), 그 역할로 사용자를 만들 수도 없습니다. API 키도 같은 역할의 키만 발급 · 수정 · 재발급 · 폐기합니다.
화면에서는 고를 수 있는 역할만 나오고 그런 행의 단추가 보이지 않으며, API 를 직접 불러도 403 입니다.

[[_사용자_정의_역할]]
== 사용자 정의 역할

슈퍼유저 · 사용자 두 역할만으로 부서 · 직무별 권한을 나누기 어려울 때 역할을 만들어 씁니다. 화면 위의 **역할** 카드에서
**역할 추가** 를 누르고 식별자 · 이름 · 기반 역할을 정합니다.

* **식별자** — 소문자로 시작하는 소문자 · 숫자 · 하이픈 3~50자(예: `data-steward`). 만든 뒤에는 바꿀 수 없습니다.
  Keycloak 을 쓰면 같은 이름의 realm 역할을 만들어 사용자에게 주세요.
* **기반 역할** — 사용자(User) 또는 슈퍼유저(Superuser). 새 역할은 기반 역할의 메뉴 · 보기 전용 · 기능 권한을 복사해 **똑같이 시작** 하고,
  그다음 표에서 이 역할의 열만 바꾸면 됩니다. 역할 이름으로 판정하는 기능(슈퍼유저 전용 작업 등)은 기반 역할을 따릅니다.
  관리자를 기반으로 하는 역할은 만들 수 없습니다.
* 만든 역할은 xref:ops/users.adoc[사용자 관리] 와 설정 › API 키에서 고를 수 있습니다. 기능을 좁힌 역할을 API 키에 주면
  그 키가 쓸 수 있는 기능도 그만큼 좁아집니다.
* 이름 · 설명 · 기반 역할은 연필 단추로 바꿉니다. 기반 역할을 바꿔도 표의 체크는 그대로입니다.
* 쓰는 사용자 · API 키가 없을 때만 지울 수 있습니다. 지우면 그 역할만 허용하던 항목은 관리자 전용으로 남습니다(모두에게 열리지 않습니다).

[[_메뉴_보기_전용]]
== 메뉴 보기 전용

**메뉴 보기 전용** 표에서 역할을 체크하면 그 역할은 메뉴를 볼 수는 있지만 편집하지 못합니다. 메뉴가 열린 역할에만 뜻이 있습니다.

* 표에는 막을 편집 기능이 있는 메뉴만 나옵니다. 대시보드 · 내 결재함 · 즐겨찾기 · AI-Ready 점검은 편집 기능이 없어 빠집니다.
  내 결재함에서 결재하는 기능(`changes.approve`)은 변경 관리 메뉴의 기능이라, 결재를 막으려면 변경 관리 메뉴를 보기 전용으로 두거나 기능 권한에서 해제하세요.

* 그 메뉴의 편집 기능(등록 · 수정 · 삭제 · 실행 등)은 기능 권한을 허용했더라도 쓸 수 없습니다. 화면에서는 단추가 숨고, 서버도 403 입니다.
  기능 권한 표에서 *조회 — 보기 전용에서도 사용* 배지가 붙은 기능(샘플 · DDL · 내려받기 · Try-it 등)은 그대로 씁니다.
* **서버 API 차단** 메뉴는 그 메뉴 API 의 쓰기 요청(조회가 아닌 요청)을 서버가 막습니다. 자기 즐겨찾기 · 저장한 보기는 예외입니다.
* 관리 메뉴를 여는 위임 권한(`datasources.sync` · `quality.manage`)은 보기 전용에 묶이지 않습니다 — 수집 계정과 관리 › 데이터 품질이 계속 동작합니다.
* 플러그인 메뉴도 같습니다. 플러그인이 기능을 메뉴에 묶어 선언했으면(백엔드 `features` 의 `menu`) 그 메뉴를 보기 전용으로 둔 역할은 그 기능을 쓸 수 없습니다.
* 보기 전용인 화면 위에는 "보기 전용 메뉴입니다" 안내 줄이 보입니다.
