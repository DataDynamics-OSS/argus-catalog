= 알림
:toc: macro
:toclevels: 2

원천 테이블의 컬럼 하나가 지워지면, 그 컬럼을 받아 쓰던 하위 테이블과 보고서가 줄줄이 깨집니다.
**알림**은 이런 변화를 **규칙**에 따라 자동으로 감지해 담당자에게 알려 주는 메뉴입니다.
스키마 변경, 리니지 매핑 영향, 품질 검증 실패, MCP 배포 위반을 감시할 수 있습니다.

이 문서는 처음 사용하는 분을 기준으로 화면(메뉴) 순서대로 설명합니다.
중간중간 나오는 **고급 사용자** 상자는 몰라도 사용에 지장이 없는 심화 내용이니 처음에는 건너뛰어도 됩니다.

toc::[]

== 시작하기 전에

=== 이런 일을 할 수 있습니다

* **규칙 만들기** — "무엇을(범위) / 언제(트리거) / 얼마나 심각하게(심각도) / 누구에게 어떻게(채널)" 알릴지 정합니다.
* **알림 확인·처리** — 생긴 알림을 걸러 보고, 확인·해결·무시로 처리합니다. 여러 건을 한 번에 처리할 수도 있습니다.
* **어디서나 확인** — 화면 위쪽 벨에서 처리할 알림 수와 최신 알림을 봅니다.
* **외부로 보내기** — Webhook 으로 Slack·Teams 등 사내 메신저에 알림을 보냅니다.

=== 먼저 알아 둘 용어

[cols="1,4",options="header"]
|===
| 용어 | 뜻

| 규칙
| 알림을 만드는 조건입니다. **활성** 규칙만 동작합니다.

| 범위(Scope)
| 감시 대상입니다. **데이터셋 / 태그 / 리니지 / 데이터 소스 / 전체** 중 하나를 고릅니다.

| 트리거
| 알림을 만드는 사건입니다. 모든 스키마 변경, 특정 변경 유형, 특정 컬럼, 매핑 컬럼 변경, 품질 검증 실패, MCP 배포 위반·보안 경고가 있습니다.

| 심각도
| **심각 / 경고 / 정보** 세 단계입니다. 자동으로 정하거나 규칙에서 강제로 정합니다.

| 상태
| 알림의 처리 단계입니다. **미확인 → 확인 → 해결**, 또는 **무시**.

| 출처 / 영향
| 출처는 변화가 일어난 데이터셋, 영향은 리니지로 이어져 영향을 받는 데이터셋입니다.
|===

=== 메뉴 위치

[cols="1,2,3",options="header"]
|===
| 메뉴 | 주소 | 용도

| 거버넌스 → 알림 → **알림** 탭 | `/dashboard/alerts` | 알림 목록, 필터, 상세, 상태 처리
| 거버넌스 → 알림 → **규칙** 탭 | `/dashboard/alerts` | 규칙 목록, 추가·수정·켜기/끄기·삭제, 도움말
| 화면 위쪽 벨 | 모든 화면 | 미확인 알림 수와 최신 알림 5건
|===

=== 누가 무엇을 할 수 있나요

[cols="3,1,1,1",options="header"]
|===
| 작업 | 일반 사용자 | 관련 데이터셋 생성자·소유자 | 관리자

| 알림·규칙 보기, 벨 보기 (로그인 필요) | ✓ | ✓ | ✓
| 알림 상태 바꾸기(확인·해결·무시·다시 열기) | – | ✓ (그 데이터셋의 알림) | ✓
| 규칙 추가·수정·켜기/끄기·삭제 | 기능 권한 `alerts.rules` 에 따름 | 〃 | ✓
| 오래된 알림 정리 | – | – | ✓
|===

"관련 데이터셋"은 알림의 **출처** 또는 **영향** 데이터셋입니다. 권한이 없는 버튼은 보이지 않습니다.

image::governance-alerts/user-readonly.png[일반 사용자 화면 — 상태 버튼이 없음, 800]

[TIP]
.고급 사용자
====
`alerts.rules` 는 **권한 관리** 메뉴의 기능(FEATURE) 권한입니다. 지정하지 않으면 **관리자만** 규칙을 관리할 수 있고,
지정한 역할은 규칙 관리와 함께 **모든 알림의 상태 변경**도 할 수 있습니다. 일반 사용자에게 규칙 탭의 Webhook 주소는 가려지고 "설정됨" 여부만 보입니다.
====

== 알림 목록

**거버넌스 → 알림** 을 열면 **알림** 탭이 나옵니다. 처음에는 **미확인** 알림만 보입니다.

image::governance-alerts/list.png[알림 목록 — 심각도·변경·출처·영향·상태·시간·작업, 800]

[cols="1,4",options="header"]
|===
| 칸 | 내용
| 심각도 | 심각(빨강) / 경고(주황) / 정보
| 변경 | 무엇이 바뀌었는지 한 줄 요약(예: "스키마 변경: 컬럼 삭제 1개")과 알림 유형·규칙 이름
| 출처 | 변화가 일어난 데이터셋(플랫폼 · 이름)
| 영향 | 리니지로 영향을 받는 데이터셋. 없으면 `-`
| 상태 | 미확인 / 확인 / 해결 / 무시. 처리한 사람이 아래에 표시됩니다
| 시간 | 알림이 생긴 시각(방금 전, 5분 전 …)
| 작업 | 지금 상태에서 할 수 있는 처리 버튼
|===

=== 걸러 보기

위쪽 세 개의 선택 상자로 **상태**(전체 상태·미확인·확인·해결·무시), **심각도**(전체 심각도·심각·경고·정보), **유형**(스키마 변경·품질 검증 실패·MCP 정책 위반·드리프트·MCP 보안 경고)을 고릅니다.
오른쪽에 걸러진 건수가 나오고, 많으면 아래쪽 **이전 / 다음** 으로 페이지를 넘깁니다.

image::governance-alerts/list-filter.png[심각도 '심각'으로 걸러 본 모습, 800]

=== 알림 상세

행을 누르면 **알림 상세** 창이 열립니다. 유형과 요약, 규칙, 출처·영향 데이터셋(누르면 데이터셋으로 이동), 컬럼별 변경 내용, 생성·처리 시각이 나오고, 아래 버튼으로 바로 처리할 수 있습니다.

image::governance-alerts/detail.png[알림 상세 — 컬럼 추가 1개, 정보, 800]

리니지 매핑이 걸린 컬럼이 바뀌면 **영향** 칸에 하위 데이터셋이 나오고, 상세에 "email (삭제) → 매핑: email"처럼 어느 컬럼이 이어져 있는지 보여 줍니다.

image::governance-alerts/detail-mapping.png[매핑 컬럼 삭제 알림 — 영향 데이터셋 it_alert.dst, 800]

TIP: 알림 주소 `/dashboard/alerts?alert=<알림 ID>` 를 열면 그 알림의 상세 창이 바로 뜹니다. 메신저로 담당자에게 알림을 넘길 때 쓰세요.

== 알림 처리

=== 상태 바꾸기

행 끝의 **작업** 버튼이나 상세 창 아래 버튼으로 상태를 바꿉니다. 지금 상태에서 갈 수 있는 버튼만 나옵니다.

[cols="1,2,3",options="header"]
|===
| 지금 상태 | 나오는 버튼 | 언제 쓰나요
| 미확인 | 확인 · 해결 · 무시 | 새로 생긴 알림
| 확인 | 해결 · 무시 · 다시 열기 | "보고 있다"고 표시한 알림
| 해결 / 무시 | 다시 열기 | 처리가 끝난 알림. 다시 문제가 되면 다시 엽니다
|===

image::governance-alerts/row-open.png[미확인 행 — 확인·해결·무시 버튼, 800]

image::governance-alerts/row-acknowledged.png[확인 후 — 해결·무시·다시 열기 버튼, 800]

image::governance-alerts/row-resolved.png[해결 후 — 다시 열기 버튼만 남음, 800]

처리한 사람과 시각은 서버가 자동으로 기록합니다(상태 칸 아래와 상세 창에 표시). **다시 열기** 를 하면 처리자 기록이 지워집니다.

=== 여러 건 한 번에 처리

행 앞의 체크박스로 여러 알림을 고르면 위쪽에 "N건 선택"과 함께 **고른 알림 모두에 공통으로 할 수 있는 처리 버튼**이 나옵니다.
처리할 수 없는 알림(권한이 없거나 이미 그 상태인 것)은 건너뛰고, 건너뛴 건수와 이유를 알려 줍니다.

image::governance-alerts/bulk.png[2건 선택 — 일괄 처리 버튼과 오래된 알림 정리, 800]

=== 오래된 알림 정리 (관리자)

관리자에게는 오른쪽 위에 **오래된 알림 정리** 버튼이 보입니다. **해결·무시된 지 90일이 지난** 알림과 전달 기록을 지웁니다. 되돌릴 수 없으니 확인 창을 잘 읽고 누르세요.

== 헤더 벨

화면 위쪽 벨의 빨간 숫자는 **미확인 알림 수**입니다(100건 이상이면 `99+`). 벨을 누르면 심각·경고 건수와 **최신 알림 5건**이 나오고, 항목을 누르면 그 알림의 상세가 열립니다. **전체 알림 보기** 로 알림 화면에 갈 수 있습니다.

image::governance-alerts/bell.png[헤더 벨 — 미확인 78건, 최신 알림, 800]

벨 숫자는 30초마다 새로 고쳐지고, 알림 화면에서 상태를 바꾸면 바로 반영됩니다.

== 규칙

**규칙** 탭에는 규칙이 카드로 나옵니다. 카드에는 심각도(자동이면 "자동"), 이름, 감시 범위, 트리거, 채널, 구독자 수, 소유자 알림 여부, 지금까지 만든 알림 수, 만든 사람, 설명이 보입니다.
오른쪽의 스위치로 규칙을 **켜고 끄고**, 연필 아이콘으로 고치고, 휴지통 아이콘으로 지웁니다.

image::governance-alerts/rules.png[규칙 탭 — 규칙 카드, 800]

규칙 탭 아래쪽의 **도움말 — 규칙은 언제 적용되나요?** 를 펼치면 평가 시점, 매칭 순서, 전달 방식, 처리 권한이 정리되어 있습니다.

image::governance-alerts/rules-help.png[규칙 탭 도움말, 800]

=== 규칙은 언제 동작하나요

규칙은 주기적으로 검사하지 않고, **사건이 기록되는 순간** 바로 평가됩니다.

* **스키마 변경** — 메타데이터 동기화에서 컬럼 추가·변경·삭제가 감지되거나, 데이터셋 상세 → 스키마 탭에서 직접 고쳐 저장했을 때
* **품질 검증 실패** — 품질 탭의 "검증 실행"이나 품질 배치 결과 반입에서 실패한 검사가 있을 때
* **MCP 배포 finding** — 정책 위반·드리프트·보안 경고가 새로 열리거나 다시 열렸을 때

NOTE: 규칙을 새로 만들거나 고쳐도 **과거 사건에는 소급되지 않습니다.** 저장한 뒤 생기는 사건부터 평가합니다.

=== 규칙 추가 — 1단계: 대상 & 조건

**규칙 추가** 를 누르면 두 단계 창이 열립니다.

image::governance-alerts/rule-step1.png[규칙 추가 1단계 — 이름·감시 대상·트리거·심각도, 800]

. **규칙 이름** — 예: "PII 데이터 컬럼 삭제 감시".
. **감시 대상 (Scope)** — 범위를 고르고, 범위에 맞는 대상을 고릅니다.
+
[cols="1,3",options="header"]
|===
| 범위 | 감시 대상
| 데이터셋 | 데이터셋 하나(검색해서 선택)
| 태그 | 그 xref:governance/tags.adoc[태그]가 붙은 모든 데이터셋. 태그를 붙이고 떼는 것만으로 대상이 바뀝니다
| 리니지 | 리니지 관계 하나(A → B). 양쪽 데이터셋의 변화를 감시합니다
| 데이터 소스 | 데이터 소스(예: Sakila MySQL)에 속한 모든 데이터셋
| 전체 | 카탈로그 전체
|===
. **트리거 (Trigger 조건)** — 무엇이 일어났을 때 알릴지 고릅니다.
+
[cols="1,3",options="header"]
|===
| 트리거 | 동작
| 모든 스키마 변경 | 컬럼 추가·변경·삭제 모두
| 스키마 변경 (변경 유형 선택) | 고른 유형(삭제·변경·추가)만. 하나 이상 골라야 합니다
| 컬럼 감시 (특정 컬럼) | 적어 둔 컬럼(콤마로 구분, 예: `amount, currency, status`)이 바뀔 때만
| 매핑 깨짐 (매핑 컬럼 변경) | 리니지 컬럼 매핑에 걸린 컬럼이 바뀔 때만. 영향 데이터셋이 함께 기록됩니다
| 품질 검증 실패 | 품질 검사가 실패할 때. **최소 실패 심각도**(정보 이상 / 경고 이상 / 심각만)로 거릅니다
| MCP 배포 정책 위반·드리프트 / MCP 배포 보안 경고 | MCP 배포 finding. **최소 심각도**와 **환경**(DEV·STG·PROD)으로 거르며, 범위는 전체·데이터 소스만 쓸 수 있습니다
|===
. **심각도** — **자동 판정**(권장) 또는 심각·경고·정보 중 하나로 **강제**합니다.
. 필요한 값이 비어 있으면 **다음** 옆에 무엇을 채워야 하는지 안내가 나오고 버튼이 잠깁니다.

image::governance-alerts/rule-column-watch.png[컬럼 감시 — 감시 컬럼을 넣기 전에는 다음 버튼이 잠김, 800]

image::governance-alerts/rule-triggers.png[트리거 선택지, 800]

품질 검증 실패 트리거로 만든 알림은 요약에 실패한 검사 이름과 점수가 나옵니다(예: "품질 검증 실패: it_alert.src — it-q-warn (점수 50.0%)").

image::governance-alerts/detail-quality.png[품질 검증 실패 알림 상세, 800]

[TIP]
.고급 사용자 — 자동 심각도
====
[cols="1,3",options="header"]
|===
| 심각도 | 기준(스키마 변경)
| 심각 | 컬럼 삭제
| 경고 | 컬럼 타입 변경
| 정보 | 컬럼 추가, 널 허용 여부만 바뀐 경우 등
|===
한 번의 변경에 여러 컬럼이 걸리면 가장 높은 심각도를 씁니다. 품질 검증 실패는 실패한 검사의 심각도를 따릅니다.
====

=== 규칙 추가 — 2단계: 알림 대상 & 방식

image::governance-alerts/rule-step2.png[규칙 추가 2단계 — 채널·구독자·소유자 알림, 800]

. 위쪽 요약에서 1단계 내용을 확인합니다(고치려면 **이전**).
. **알림 채널** 을 고릅니다.
** **앱 내** — 알림 탭과 헤더 벨에 표시하고, 구독자와 소유자를 수신자로 기록합니다.
** **Webhook** — 고르면 **Webhook URL** 칸이 나옵니다. `http://` 또는 `https://` 로 시작하는 주소를 넣으세요(예: Slack Incoming Webhook). 알림 1건마다 한 번 보내고, 성공·실패가 기록됩니다.
** 이메일은 아직 지원하지 않습니다.
. **구독자** — 알림을 받을 사용자 이름을 콤마로 적습니다(예: `alice, security-team`).
. **데이터셋 소유자에게도 알림** — 켜면 관련 데이터셋의 소유자도 수신자가 됩니다(MCP 트리거는 "MCP 배포 소유자에게도 알림").
. **설명** 을 적고 **규칙 저장** 을 누릅니다.

=== 규칙 고치기·끄기·지우기

* **끄기** — 카드의 스위치를 끄면 "비활성"으로 표시되고, 그동안 생기는 사건은 평가하지 않습니다. 잠시 멈출 때는 지우지 말고 끄세요.
* **고치기** — 연필 아이콘을 누르면 같은 두 단계 창이 **알림 규칙 수정** 으로 열립니다.
* **지우기** — 휴지통 아이콘을 누르면 확인 창이 뜹니다. 이미 생긴 알림은 남지만 규칙 연결은 끊어지고, 알림 상세의 규칙 칸에는 "(삭제된 규칙)"으로 나옵니다.

[TIP]
.고급 사용자 — Webhook 으로 받는 내용
====
알림 1건마다 다음과 같은 JSON 을 POST 합니다. `text` 필드는 Slack Incoming Webhook 과 호환되어 그대로 메시지로 보입니다.

  "alert_id": 482,
  "alert_type": "SCHEMA_CHANGE",
  "severity": "BREAKING",
  "rule_name": "it-rule-mapping",
  "source":   { "dataset": "it_alert.src", "datasource": "postgresql" },
  "affected": { "dataset": "it_alert.dst", "datasource": "postgresql" },
  "entity": null,
  "change_summary": "매핑 컬럼 변경: 'email' 삭제 (매핑: email)",
  "changes": [
    { "changed_column": "email", "mapped_to": "email", "change_type": "DROP", "severity": "BREAKING",
      "before": { "field_type": "VARCHAR(100)" }, "after": null }

|===
| 목적 | 범위 | 트리거 | 채널

== 자주 묻는 질문·문제 해결

[qanda]
규칙을 만들었는데 알림이 생기지 않습니다.::
  규칙이 **활성**인지, 범위 대상이 맞는지 확인하세요. 규칙은 저장한 뒤 생긴 사건부터 평가하고, 과거 변경에는 소급되지 않습니다. 범위 대상(데이터셋·태그 등)이 지워진 규칙은 동작하지 않습니다.

같은 변경에 알림이 여러 개 생깁니다.::
  같은 데이터셋을 감시하는 활성 규칙이 여럿이면 규칙마다 알림이 하나씩 생깁니다. 목록의 "규칙:" 표시로 어느 규칙이 만든 알림인지 확인하고, 겹치는 규칙은 끄거나 범위를 좁히세요.

다음 버튼이 눌리지 않습니다.::
  버튼 옆 안내 문구를 확인하세요. 범위 대상을 고르지 않았거나, 변경 유형·감시 컬럼이 비어 있는 경우입니다.

Webhook 이 오지 않습니다.::
  URL 이 `http(s)://` 로 시작하는지, 카탈로그 서버에서 그 주소로 접속할 수 있는지 확인하세요. 실패한 전송은 전달 기록에 실패로 남습니다.

이메일로 받을 수 있나요?::
  아직 지원하지 않습니다. Webhook 으로 사내 메신저에 보내세요.

상태 버튼이 보이지 않습니다.::
  알림의 출처·영향 데이터셋을 만든 사람이나 소유자, 또는 규칙 관리 권한(`alerts.rules`)이 있는 사람만 상태를 바꿀 수 있습니다.

벨 숫자가 바로 줄지 않습니다.::
  다른 화면에서 일어난 변경은 30초 안에 반영됩니다. 알림 화면에서 처리한 것은 바로 반영됩니다.

== 부록 — REST API 로 쓰기

기본 경로는 `/api/v1/alerts` 이며, 모든 호출에 로그인 토큰(`Authorization: Bearer <토큰>`)이 필요합니다.

[cols="2,3",options="header"]
|===
| 엔드포인트 | 설명

| `GET /alerts` | 목록(`status`, `severity`, `alert_type`, `dataset_id`, `page`, `page_size`)
| `GET /alerts/{id}` | 상세
| `GET /alerts/summary` | 미확인 건수(전체·심각·경고·정보) — 헤더 벨
| `PUT /alerts/{id}/status` | 상태 변경 `{"status": "ACKNOWLEDGED"\|"RESOLVED"\|"DISMISSED"\|"OPEN"}`
| `POST /alerts/bulk-status` | 일괄 상태 변경 `{"ids": [...], "status": "..."}` → `{updated, skipped}`
| `DELETE /alerts/closed?older_than_days=90` | 오래된 알림 정리(관리자)
| `GET·POST /alerts/rules`, `GET·PUT·DELETE /alerts/rules/{id}` | 규칙
|===

[source,bash]
----
# 미확인 심각 알림 5건
curl -H "Authorization: Bearer $TOKEN" "$CATALOG/api/v1/alerts?status=OPEN&severity=BREAKING&page_size=5"
----
