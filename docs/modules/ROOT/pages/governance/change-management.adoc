= 변경 관리 (Change Management)
:toc: macro
:toclevels: 2

데이터셋의 스키마나 메타데이터를 바꾸기 전에 **변경 요청(CR, Change Request)** 을 작성해 결재를 받는 화면입니다.
결재가 모두 승인되면 정해 둔 시각에 카탈로그의 스키마가 자동으로 바뀌고, 이 데이터를 쓰는 사람들에게 알림이 갑니다.

이 문서는 처음 사용하는 분을 기준으로 작업 순서대로 설명합니다.
중간중간 나오는 **고급 사용자** 상자는 몰라도 사용에 지장이 없는 심화 내용이니 처음에는 건너뛰어도 됩니다.

== 시작하기 전에

=== 이런 일을 할 수 있습니다

* **변경 요청 만들기** — 바꿀 컬럼(추가·수정·삭제)과 사유·롤백 계획을 적습니다.
* **결재 올리기(상신)** — 결재선의 결재자가 순서대로 승인합니다. 상신하면 리니지를 따라 영향받는 데이터셋과 소비자를 자동으로 분석합니다.
* **내 결재함에서 결재하기** — 내 차례인 요청만 모아 보고 승인하거나 반려합니다.
* **자동 적용과 통지** — 승인되면 예정 시각에 스키마를 적용하고, 소비자와 참조자에게 알립니다.
* **취소** — 적용되기 전까지는 언제든 취소할 수 있습니다.

=== 먼저 알아 둘 용어

[cols="1,4",options="header"]
|===
| 용어 | 뜻

| 변경 요청(CR)
| 결재를 받기 위한 문서입니다. 코드는 `CR-연도-일련번호` 형식으로 자동으로 매겨집니다.

| 상신
| 작성한 변경 요청을 결재선에 올리는 것입니다.

| 결재선
| 결재자를 순서대로 나열한 목록입니다. 앞 단계가 승인해야 다음 결재자 차례가 됩니다.

| 참조자(CC)
| 결재권 없이 변경 내용을 통지받는 사용자입니다.

| 소비자
| 데이터셋을 쓰는 시스템·팀입니다. 영향 분석의 소비자 수와 적용 통지의 대상이 됩니다.
|===

=== 메뉴 위치

좌측 사이드바 **데이터 카탈로그** 아래 두 메뉴를 씁니다.

[cols="1,2,3",options="header"]
|===
| 메뉴 | 주소 | 용도

| 변경 관리 | `/dashboard/changes` | 변경 요청 목록 · 생성 · 상세
| 내 결재함 | `/dashboard/my-approvals` | 지금 내가 결재할 차례인 변경 요청만 모아 봅니다. 메뉴 옆 숫자 배지가 대기 건수입니다.
| 데이터셋 상세 → 더보기 → 변경 요청 | `/dashboard/datasets/{id}` | 그 데이터셋의 변경 요청만 봅니다(<<_데이터셋에서_보기>> 참고).
|===

=== 누가 무엇을 할 수 있나요

화면을 쓰려면 로그인해야 하고, 권한 관리에서 두 메뉴가 열려 있어야 합니다.

[cols="1,3",options="header"]
|===
| 작업 | 할 수 있는 사람

| 목록 · 상세 조회
| 로그인한 사용자 누구나
| 변경 요청 생성
| 기능 권한 **변경 요청 생성** (`changes.create`)이 있는 사용자
| 결재 상신 · 취소
| 그 변경 요청을 만든 사람(요청자) 또는 관리자
| 승인 · 반려
| **지금 차례인 결재자 본인** 이면서 기능 권한 **변경 요청 결재** (`changes.approve`)가 있는 사용자
| 데이터 소비자 등록
| 기능 권한 **데이터 소비자 등록** (`changes.consumers`)이 있는 사용자(API 전용)
| 참조자 통지 설정
| 관리자
|===

권한이 없으면 **변경 요청 생성** · **새 변경 요청** 버튼과 승인 · 반려 버튼이 화면에 나타나지 않습니다.

NOTE: 요청자가 자기 변경 요청의 결재자가 되는 것은 막지 않습니다. 결재선을 정할 때 조직 규칙에 맞게 지정하세요.

=== 변경 요청의 상태

변경 요청은 다음 상태를 거칩니다. 화면에는 한글 상태 배지로 표시됩니다.

[cols="1,1,3",options="header"]
|===
| 상태 | 화면 표시 | 의미

| `DRAFT` | 임시저장 | 작성만 하고 아직 상신하지 않은 상태입니다. 이때만 **결재 상신** 할 수 있습니다.
| `SUBMITTED` | 상신됨 | 상신 직후 영향 분석이 진행 중인 상태입니다. 보통 1~2초 안에 다음 상태로 넘어갑니다.
| `APPROVING` | 결재중 | 결재선의 결재를 기다리는 상태입니다. **승인 · 반려는 이 상태에서만** 할 수 있습니다.
| `APPROVED` | 승인됨 | 모든 결재가 끝나고 적용 예정 시각을 기다리는 상태입니다.
| `APPLIED` | 적용완료 | 스키마 변경이 데이터셋에 반영된 최종 상태입니다.
| `REJECTED` | 반려됨 | 결재자가 반려했거나, 한 단계가 7일 안에 결재되지 않아 기한이 지난 상태입니다.
| `CANCELLED` | 취소됨 | 요청자나 관리자가 적용 전에 취소한 상태입니다.
|===

* 결재선이 없는 변경 요청은 영향 분석이 끝나면 곧바로 **승인됨** 이 되고, 적용 예정 시각이 없거나 이미 지났으면 바로 **적용완료** 가 됩니다.
* 승인 · 반려 · 취소는 뒤에서 비동기로 처리됩니다. 버튼을 누른 직후에는 상태가 그대로일 수 있으니 잠시 뒤 **새로고침** 하세요.

== 변경 요청 목록 보기

**변경 관리** 메뉴를 누르면 변경 요청이 표로 나옵니다.

image::governance-change-management/list.png[변경 관리 목록 — 결재중 · 반려됨 · 적용완료 변경 요청과 결재 진행 열, 900]

* 위쪽 탭 **전체** · **내 요청** · **내 결재 대기** 로 범위를 바꿉니다. 탭 옆 숫자가 건수입니다.
* 열은 코드 · 제목 · 상태 · 유형 · 우선순위 · 요청자 · 결재 · 적용 예정 · 생성일입니다. **적용 예정** · **생성일** 은 머리글을 눌러 정렬합니다.
* **결재** 열은 처리된 단계 / 전체 단계(예: `1/2`)입니다. 반려(기한 초과 포함)되면 빨간 `반려`, 취소로 남은 단계가 있으면 회색 `n/전체 (중단)`, 결재선이 없으면 `—` 로 보입니다.
* 행을 누르면(또는 행에 포커스를 두고 Enter) 상세 화면으로 이동합니다.

TIP: 목록에는 상태나 데이터셋으로 거르는 입력이 없습니다. 특정 데이터셋의 변경 요청만 보려면 아래 데이터셋 상세의 **변경 요청** 탭을 쓰세요.

[#_데이터셋에서_보기]
=== 데이터셋에서 보기

. 데이터셋 상세에서 탭 **더보기** › **변경 요청** 을 엽니다.
. 그 데이터셋에 대한 변경 요청이 카드로 나옵니다. 카드에는 코드 · 제목 · 상태 · 유형 · 우선순위 · 요청자 · 생성일 · 적용 예정이 표시됩니다.
. 카드를 누르면 상세로 이동합니다.

변경 요청이 없으면 "이 데이터셋에 대한 변경 요청이 없습니다." 가 보입니다.

image::governance-change-management/dataset-tab.png[데이터셋 상세의 변경 요청 탭, 900]

이 탭의 **새 변경 요청** 버튼으로 생성 화면을 열면 **대상 데이터셋** 이 그 데이터셋으로 고정됩니다.

== 변경 요청 만들기

. **변경 관리** 의 **변경 요청 생성** 버튼(또는 데이터셋 탭의 **새 변경 요청**)을 누릅니다.
. 기본 정보를 적습니다(아래 표).
. **스키마 변경** 표에서 바꿀 컬럼을 고칩니다.
. 결재선과 참조자를 정합니다.
. **생성** 을 누릅니다.

=== 기본 정보

[cols="1,3",options="header"]
|===
| 항목 | 설명

| 제목 **(필수)**
| 변경 내용을 한 줄로 적습니다. 예: 고객 테이블 컬럼 추가
| 대상 데이터셋 **(필수)**
| **데이터셋 검색...** 에 이름을 입력해 고릅니다. 고른 뒤 **변경** 으로 다시 고를 수 있습니다. 데이터셋 화면에서 들어왔으면 고정되어 있습니다.
| 변경 유형
| **호환성 깨짐 (Breaking)** · **호환 유지 (Non-breaking)** · **추가 (Additive)** · **표기·메타데이터 (Cosmetic)** 중 하나입니다.
| 우선순위
| **긴급** · **높음** · **보통** (기본) · **낮음** 중 하나입니다.
| 설명
| 서식 편집기로 변경 내용을 자세히 적습니다. **스키마 추가** 를 누르면 대상 데이터셋의 현재 스키마 표(컬럼 · 타입 · Null · 키 · 설명)가 편집기에 들어갑니다.
| 롤백 계획 **(필수)**
| 실패 시 되돌리는 방법입니다.
| 업무 사유 **(필수)**
| 변경이 필요한 비즈니스 사유입니다. 상세 화면에는 **비즈니스 근거** 로 표시됩니다.
| 적용 예정 시각
| 승인 후 실제로 적용할 시각입니다. 브라우저 시간대 기준으로 입력하며, 비워 두면 승인 즉시 적용합니다.
|===

어떤 변경 유형을 고를지 모르겠다면 **변경 유형 · 우선순위 도움말 (펼치기)** 를 누르세요. 요약하면 다음과 같습니다.

[cols="1,3",options="header"]
|===
| 변경 유형 | 언제 고르나

| 호환성 깨짐 (Breaking)
| 컬럼 삭제 · 타입 변경 · 필수화처럼 기존 소비자가 깨지는 변경
| 호환 유지 (Non-breaking)
| 기본값 변경 · 길이 확장처럼 기존 사용에 영향이 없는 변경
| 추가 (Additive)
| 선택 컬럼 신설처럼 순수하게 추가만 하는 변경
| 표기·메타데이터 (Cosmetic)
| 설명 · 태그 · 표기 변경. 스키마 입력이 필요 없어 스키마 변경 표가 숨겨집니다.
|===

=== 스키마 변경

대상 데이터셋을 고르면 **스키마 변경** 표에 현재 스키마가 미리 채워집니다. 승인되면 이 표에서 바꾼 내용이
데이터셋 스키마에 그대로 적용됩니다.

* **수정** — **타입** · **NULL** 을 바꾸면 그 행에 주황 `수정` 배지가 붙고, 타입 칸 아래에 기존 값이 보입니다.
* **추가** — **컬럼 추가** 로 새 행을 넣고 이름 · 타입을 적으면 초록 `추가` 배지가 붙습니다.
* **삭제** — 행 오른쪽 휴지통(**컬럼 삭제**)을 누르면 빨간 `삭제` 배지와 취소선이 생깁니다. 같은 자리 버튼으로 **삭제 취소** 할 수 있습니다.
* 표 아래에 바뀐 건수(`변경 3건`)가 보이고, **초기화** 로 처음 상태로 되돌립니다.
* 바꾼 내용이 고른 유형보다 커 보이면 "변경 내용상 「호환성 깨짐 (Breaking)」 유형으로 보입니다. **변경 유형 바꾸기**" 안내가 나옵니다. 링크를 누르면 유형이 바뀝니다.

image::governance-change-management/create-schema-change.png[스키마 변경 표 — 수정 · 삭제 · 추가 배지와 변경 건수, 유형 제안, 900]

새 컬럼 이름을 비워 두면 "신규 컬럼 이름을 입력하세요.", 기존 컬럼과 이름이 같으면 "컬럼 'x' 이(가) 이미 있습니다." 가 표시되고 생성이 막힙니다.

NOTE: 설명 편집기의 **스키마 추가** 는 현재 스키마를 참고 자료로 붙여 넣는 기능입니다. 실제로 적용되는 내용은 위 **스키마 변경** 표뿐입니다.

image::governance-change-management/insert-schema-table.png[스키마 추가 — 설명 편집기에 현재 스키마 표 삽입, 900]

=== 결재선과 참조자

[cols="1,3",options="header"]
|===
| 항목 | 설명

| 결재선 (순서대로)
| 결재자를 순서대로 고릅니다. 처음에 1행이 있고, **결재자 추가** 로 행을 늘립니다. 고르지 않은(`미지정`) 행은 저장되지 않습니다. 결재선을 모두 비우면 결재 없이 진행됩니다.
| 참조자 (CC) — 생성 시 통지
| **참조자 추가** 로 등록된 사용자 중에서 고릅니다. 통지 채널은 관리자가 전역으로 정합니다(<<_참조자_통지_설정>>).
|===

=== 생성

**생성** 을 누르면 변경 요청이 **임시저장** 상태로 만들어지고 목록으로 돌아갑니다. "변경 요청 'CR-2026-NNNN' 을(를) 만들었습니다." 안내가 뜨고, 참조자에게는 이 시점에 통지가 나갑니다.

* 제목 · 대상 데이터셋 · 롤백 계획 · 업무 사유 중 하나라도 비어 있으면 "필수 항목(제목·대상 데이터셋·롤백 계획·업무 사유)을 입력하세요." 가 표시됩니다.
* 스키마를 하나도 바꾸지 않고 생성하면 확인 창이 한 번 더 뜹니다. 표기 · 메타데이터 변경처럼 일부러 스키마를 바꾸지 않는 경우에만 **생성** 을 누르세요.

image::governance-change-management/no-schema-change-confirm.png[스키마 변경 없이 생성 확인 창, 700]

== 결재 올리기(상신)

. 목록에서 변경 요청을 열어 상세 화면으로 들어갑니다.
. 오른쪽 위 **결재 상신** 을 누릅니다(요청자나 관리자에게만 보입니다).
. 상태가 **상신됨** 으로 바뀌고 영향 분석이 자동으로 진행됩니다.
. 분석이 끝나면 **결재중** 이 되고, 1단계 결재자의 결재함에 들어갑니다.

상세 화면은 **개요** · **설명** · **스키마 변경** · **결재선** · **참조자 (CC)** · **롤백 계획** · **비즈니스 근거** · **영향 분석** · **알림 발송 이력** 섹션으로 되어 있습니다.
**개요** 의 대상 데이터셋 이름을 누르면 그 데이터셋 상세로 이동합니다.

image::governance-change-management/detail-draft.png[임시저장 상세 — 오른쪽 위 결재 상신 · 취소 버튼, 900]

image::governance-change-management/detail-approving.png[상신 후 결재중 — 1단계 결재자 행에 승인 · 반려 버튼, 900]

=== 영향 분석 결과 읽기

상신하면 리니지를 따라 이 변경이 어디에 영향을 주는지 자동으로 분석합니다. 결과는 상세의 **영향 분석** 섹션에 JSON 으로 표시됩니다.
가장 먼저 `summary`(한 줄 요약)와 `risk_score`(위험도)를 보세요.

[cols="1,3",options="header"]
|===
| 항목 | 의미

| `summary` | 한 줄 요약. 예: "다운스트림 1개 데이터셋, 컬럼 영향 1건, 소비자 1명(중대 1) — 위험도 0.71"
| `risk_score` | 변경 유형 · 영향 범위 · 중대 소비자를 합친 0~1 사이 위험도
| `changed_columns` | 바뀌는 컬럼 목록
| `affected_downstream_count` · `affected_dataset_ids` | 리니지상 영향받는 다운스트림 데이터셋 수와 ID
| `affected_columns` | 컬럼 매핑으로 이어진 다운스트림 컬럼(`<데이터셋 ID>.<컬럼>`)
| `affected_consumer_count` · `mission_critical_consumers` | 영향받는 등록 소비자 수와 그중 중대(MISSION_CRITICAL) 소비자 수
|===

image::governance-change-management/detail-step2-impact.png[1단계 승인 후 2단계 결재 대기와 영향 분석 결과, 900]

TIP: 영향 분석은 리니지와 컬럼 매핑을 기준으로 합니다. 다운스트림 리니지가 정확해야 결과가 의미 있으니
xref:catalog/lineage.adoc[리니지] 를 먼저 정비해 두세요.

[TIP]
.고급 사용자 — 데이터 소비자 등록
====
소비자 등록 화면은 아직 없고 API(`POST /api/v1/changes/consumers`)로만 등록합니다. 등록할 때 이름 ·
유형 · 용도 · 중요도(예: `MISSION_CRITICAL`) · 연락 이메일 · Webhook 주소를 정할 수 있습니다.
등록된 소비자는 상세의 **알림 발송 이력** 에 수신처 이름으로 보입니다.
====

[TIP]
.고급 사용자 — Temporal 워크플로와 결재 워커
====
결재 진행과 적용은 Temporal 워크플로 엔진 위에서 동작하는 **결재 워커**(`argus-catalog-worker`)가 처리합니다.
상신하면 Temporal 에 `cr-<변경 요청 코드>` (예: `cr-CR-2026-9001`) 이름의 `ChangeApprovalWorkflow` 가 시작됩니다.
운영자는 Temporal UI 에서 이 이름으로 진행 상황을 볼 수 있습니다.

image::governance-change-management/temporal-workflow.png[Temporal UI — 결재 대기 중인 변경 요청 워크플로, 900]

* 변경 요청 작성 · 조회는 Temporal 없이도 됩니다.
* Temporal 에 연결할 수 없으면 **결재 상신** 이 "결재를 상신하지 못했습니다." 오류로 실패하고 변경 요청은 **임시저장** 으로 남습니다. Temporal 이 다시 살아나면 백엔드를 재시작하지 않아도 다음 상신부터 정상 동작합니다.
* 워커가 떠 있지 않으면 상신은 되지만 **상신됨** 에서 멈춥니다. 워커 상태를 확인하세요.

배포 구성은 xref:install/docker.adoc[Docker Compose 배포] 를 참고하세요.
====

== 결재하기

=== 내 결재함

**내 결재함** 은 "지금 내가 결재할 차례인 변경 요청 N건" 을 카드로 보여 줍니다. 카드에는 코드 · 제목 · 상태 ·
유형 · 우선순위 · 요청자 · 기한이 있고, 기한이 지나면 빨간 `(지연)` 이 붙습니다. 카드를 누르면 상세로 이동합니다.

image::governance-change-management/my-approvals.png[내 결재함 — 사이드바 배지와 승인 · 반려 버튼, 900]

* 사이드바 **내 결재함** 배지는 1분마다, 그리고 화면을 이동할 때 갱신됩니다.
* 다음 단계 결재자에게는 앞 단계가 끝나야 카드가 나타납니다. 차례가 아니면 결재함은 비어 있고 상세 결재선에도 버튼이 없습니다.
* 결재중이 아닌 변경 요청(반려 · 취소 · 적용 완료)은 결재함에 나오지 않습니다.

image::governance-change-management/not-my-turn.png[2단계 결재자가 연 상세 — 아직 차례가 아니어서 버튼 없음, 900]

=== 승인과 반려

. 내 결재함 카드나 상세 **결재선** 의 내 행을 찾습니다.
. 버튼을 누릅니다.
** **승인** — 의견 입력 없이 바로 처리됩니다. 다음 단계가 있으면 다음 결재자에게 넘어가고, 마지막 단계면 **승인됨** 이 됩니다.
** **반려** — "반려" 대화상자가 뜹니다. **반려 사유 (선택)** 에 요청자에게 전달할 사유를 적고 **반려** 를 누르면 즉시 **반려됨** 이 됩니다. 대화상자에서 **취소** 를 누르면 보내지 않습니다.

image::governance-change-management/reject-dialog.png[반려 사유 입력 대화상자, 700]

반려되면 결재선의 해당 행에 빨간 X 아이콘과 사유가 표시되고, 남은 단계는 회색 아이콘과 `진행 안 함` 배지로 바뀝니다.
데이터셋 스키마는 바뀌지 않습니다.

image::governance-change-management/detail-rejected.png[반려됨 상세 — 1단계 반려 사유, 2단계 진행 안 함, 900]

IMPORTANT: 각 단계는 **7일** 안에 결재해야 합니다. 기한이 지나면 변경 요청이 자동으로 **반려됨** 이 됩니다.

결재선 아이콘의 의미는 다음과 같습니다.

[cols="1,3",options="header"]
|===
| 표시 | 의미

| 주황 시계 | 결재 대기
| 초록 체크 + 시각 | 승인
| 빨간 X + 사유 | 반려
| 회색 원 + `위임 → <대결자>` | 위임 처리됨(아래 고급 상자 참고)
| 회색 + `진행 안 함` | 반려 · 취소 · 기한 초과로 끝나 진행되지 않은 단계
|===

[TIP]
.고급 사용자 — 위임
====
**위임** 은 화면 버튼 없이 API(`POST /api/v1/changes/{id}/decisions`, `decision=DELEGATED`, `delegated_to` 필수)로만 할 수 있습니다.
현재는 대결자에게 결재가 넘어가지 않고, 위임 기록만 남긴 채 승인처럼 다음 단계로 진행합니다.

image::governance-change-management/delegated.png[위임 처리된 1단계 — 위임 대상 배지와 사유, 900]
====

== 적용과 통지 확인하기

마지막 결재가 승인되면 다음 순서로 자동 진행됩니다. 따로 할 일은 없습니다.

. 상태가 **승인됨** 으로 바뀝니다.
. 적용 예정 시각이 있으면 예정 7일 전(`D-7`)과 1일 전(`D-1`)에 소비자에게 사전 통지를 보냅니다. 그 시점이 이미 지났으면 바로 보냅니다.
. 예정 시각까지 기다립니다(없으면 기다리지 않음).
. 스키마 변경을 데이터셋에 적용하고 스키마 이력에 스냅샷을 남깁니다. 상태는 **적용완료** 가 되고 **개요** 의 **적용 완료** 에 시각이 기록됩니다.
. 소비자에게 적용(`적용`) 통지를 보냅니다.

image::governance-change-management/detail-applied.png[적용완료 상세 — 결재선 두 단계 승인 시각, 900]

적용된 스키마는 데이터셋 상세의 스키마와 스키마 이력에서 확인할 수 있습니다(xref:catalog/schema.adoc[스키마] 참고).

=== 알림 발송 이력

상세 아래 **알림 발송 이력** 표는 이 변경 요청으로 나간 모든 통지를 보여 줍니다.

[cols="1,3",options="header"]
|===
| 열 | 값

| 채널 | 이메일 · Slack · Mattermost · Webhook · 인앱
| 단계 | 상신(참조자 통지) · D-7 · D-1 · 적용
| 수신처 | 참조자 이메일 · 이름, 또는 소비자 이름
| 상태 | 발송됨 · 전달됨(Webhook 수신 확인) · 확인됨(수신 측 확인) · 실패 · 대기
| 발송 시각 | 보낸 시각
|===

image::governance-change-management/notification-log.png[알림 발송 이력 — 인앱 · Webhook 적용 통지와 참조자 이메일, 900]

적용 예정 시각을 정한 변경 요청은 사전 통지까지 함께 기록됩니다.

image::governance-change-management/notification-phased.png[적용 예정 변경 요청의 D-7 · D-1 · 적용 Webhook 통지, 900]

화면에서 상신하면 소비자 통지 채널은 **이메일** 과 **인앱** 입니다.

[TIP]
.고급 사용자 — Webhook 통지와 수신 확인
====
* 소비자 Webhook 으로 보내려면 API 로 상신하면서 채널에 `WEBHOOK` 을 넣습니다(`POST /api/v1/changes/{id}/submit`, 본문 `["WEBHOOK","IN_APP"]`).
* Webhook 통지 본문에는 이벤트(`schema_change_notification`) · 단계 · 변경 요청 코드 · 데이터셋 · 변경 전후 스키마 · 영향 분석이 들어 있습니다.
* 수신 측이 통지를 확인하면 API(`POST /api/v1/changes/notifications/{id}/ack`)로 확인 처리할 수 있고, 표의 상태가 **확인됨** 으로 바뀝니다.
====

== 변경 요청 취소

요청자나 관리자는 적용되기 전(**임시저장** · **상신됨** · **결재중** · **승인됨**)까지 취소할 수 있습니다.

. 상세 오른쪽 위 **취소** 를 누릅니다.
. "변경 요청 취소" 대화상자에서 **요청 취소** 를 누릅니다. **닫기** 를 누르면 그대로 둡니다.

image::governance-change-management/cancel-confirm.png[변경 요청 취소 확인 대화상자, 700]

* **임시저장** 은 바로 **취소됨** 이 됩니다.
* 상신 후에는 결재 대기 중이든 승인 후 적용 예정 시각을 기다리는 중이든 곧바로 **취소됨** 이 됩니다. 스키마는 바뀌지 않습니다.
* **적용완료** · **반려됨** · **취소됨** 상태에는 **취소** 버튼이 없습니다.

image::governance-change-management/approved-waiting.png[승인 후 적용 예정 시각을 기다리는 변경 요청 — 취소 가능, 900]

NOTE: 취소된 변경 요청은 다시 상신할 수 없습니다. 같은 변경이 필요하면 새로 만드세요.

[#_참조자_통지_설정]
== 참조자 통지 설정 (관리자)

참조자(CC)에게 보내는 생성 통지는 관리자가 정합니다.

. **설정** › **연동** › **변경관리** 를 엽니다.
. "변경관리 참조자 통지" 카드에서 다음을 정합니다.
** **참조자 통지 활성화** — 끄면 참조자에게 아무 통지도 보내지 않습니다.
** **통지 채널** — **이메일** 은 참조자별 주소로 보내고, **Slack** · **Mattermost** 는 **연동** › **알림** 에 등록한 기본 Webhook 으로 참조자 이름을 모아 한 번에 보냅니다.

image::governance-change-management/settings-referrer-notify.png[설정 › 연동 › 변경관리 — 참조자 통지 활성화와 채널, 900]

이메일로 보내려면 **연동** › **이메일** 의 SMTP 설정이 켜져 있어야 합니다(xref:ops/settings.adoc[설정] 참고).
채널이 Slack 이면 알림 발송 이력에 참조자마다 `Slack` · `상신` 행이 남습니다.

image::governance-change-management/referrer-slack-log.png[Slack 채널로 보낸 참조자 통지 이력, 900]

== 자주 묻는 질문

[qanda]
**결재 상신** 이 "결재를 상신하지 못했습니다." 로 실패합니다.::
  결재 엔진(Temporal)에 연결할 수 없는 상태입니다. 변경 요청은 **임시저장** 으로 남으니 운영자에게 알리고, 복구된 뒤 다시 상신하세요. 백엔드 재시작은 필요 없습니다.

상신했는데 **상신됨** 에서 넘어가지 않습니다.::
  결재 워커가 떠 있지 않을 때 생깁니다. 운영자에게 워커 상태 확인을 요청하세요(위 Temporal 고급 상자 참고).

승인·반려를 눌렀는데 상태가 그대로입니다.::
  뒤에서 비동기로 처리됩니다. 잠시 뒤 **새로고침** 하세요.

결재자로 지정됐는데 결재함이 비어 있습니다.::
  앞 단계 결재가 아직 끝나지 않았습니다. 내 차례가 되어야 카드와 버튼이 나타납니다.

**변경 요청 생성** 버튼이나 승인·반려 버튼이 보이지 않습니다.::
  기능 권한(`changes.create` · `changes.approve`)이 막혀 있습니다. 관리자에게 요청하세요.

취소한 변경 요청을 다시 올릴 수 있나요?::
  없습니다. 같은 내용으로 새 변경 요청을 만드세요.

데이터셋을 삭제하면 변경 요청은 어떻게 되나요?::
  데이터셋이나 데이터 소스를 삭제하면 딸린 변경 요청도 결재 단계 · 참조자 · 통지 이력과 함께 삭제됩니다.
  데이터 소스 삭제 대화상자에 "데이터셋의 변경 요청 N건이 함께 삭제됩니다." 로 미리 안내되고, 진행 중이던 결재 워크플로에는 자동으로 취소 신호를 보냅니다.

== 부록: REST API

기본 경로는 `/api/v1/changes` 이며, 조회를 포함해 모두 로그인 토큰이 필요합니다.

[cols="2,3",options="header"]
|===
| 엔드포인트 | 설명

| `POST /changes` | 변경 요청 생성(`changes.create`)
| `GET /changes` | 목록(`status` · `dataset_id` 필터)
| `GET /changes/inbox` · `GET /changes/inbox/count` | 내 결재함 목록 · 건수
| `GET /changes/{id}` | 상세
| `POST /changes/{id}/submit` | 결재 상신. 본문은 소비자 통지 채널 배열(예: `["EMAIL","IN_APP"]`)
| `POST /changes/{id}/decisions` | 결재 결정 — `APPROVED` · `REJECTED` · `DELEGATED`(`changes.approve`, 현재 차례 결재자 본인)
| `POST /changes/{id}/cancel` | 취소
| `POST /changes/consumers` · `GET /changes/consumers/{dataset_id}` | 소비자 등록(`changes.consumers`) · 조회
| `GET /changes/{id}/notifications` | 알림 발송 이력
| `POST /changes/notifications/{id}/ack` | 통지 확인 처리
|===

결재 결정과 취소는 `202 Accepted` 로 접수만 하고 실제 상태 변경은 워커가 처리합니다.
결재중이 아닌 변경 요청에 결정을 보내면 `409`, 차례가 아닌 결재자는 `403` 으로 거절됩니다.
